## 长期方向：依赖前置条件，暂不适合近期排期

### 双模型分工：专精古籍大模型 + DeepSeek 苏格拉底人格

用户了解到国内有专门针对文言文/古籍训练的大模型（查证属实，例如北师大"AI太炎2.0"、华南理工"通古大模型"、南京农业大学"荀子大语言模型"，均为高校研发的专精模型），相比通用的DeepSeek，在古籍文本理解、字词训诂、用典分析上更准确。用户担心的点：现在DeepSeek+提示词调出来的苏格拉底"性格"和犀利的提问方式效果很好，不希望为了补知识准确性而推翻重做。

**架构方向（不是替代，是分工）**：不做"两个模型同时回答/竞争"的复杂架构，而是让专精模型负责"这段原文准确说了什么、有没有典故、字词怎么解"，DeepSeek继续负责"怎么用苏格拉底方式对话"——专精模型的解读作为背景知识喂给DeepSeek，苏格拉底人格和提示词完全不用动。可以复用"TTS拼音标注"同一套架构模式：书导入书库时让专精模型对全文做一次性深度解读并存下来，用户提问时直接把预先算好的解读喂给DeepSeek当背景知识，不用每次现场调用两个模型（省成本、省延迟）。

**前提条件**：需要先查证这几个学术模型是否有对外开放、可用于生产环境的API（不能假设它们都像DeepSeek一样现成可用，有可能只是研究/演示性质），这个待真正推进到这一步时再核实。属于长期愿景，不着急。

### 知识图谱式关联呈现（2026-07-26 完整方案讨论）

复盘页"关联主题"板块长期设想做成"星系/星球式"的图形结构，用可视化工具做过力导向图交互demo验证过方向（节点可拖动、点击居中）。技术上是 GraphRAG / AI第二大脑这一类已经在业界跑通的模式（Obsidian、Mem.ai、微软GraphRAG研究），不是凭空发明，具体到本产品的技术链路：

1. **概念提取**（新增，AI生成）：每条划线/问答提炼出1-3个核心概念词，不是用原文当节点
2. **概念去重/合并**：对提取出的关键词再做一次向量聚类，把说法不同但意思一样的合并成一个canonical节点
3. **节点间连线**：复用已有的关联检测机制，作用对象从"原始记录"换成"概念节点"
4. **节点大小=触及深度**：等于这个概念底下挂了多少条划线/问答，越大代表用户越常回来思考，不是随便定的视觉大小
5. **点节点能看到真实依据**（原始划线/问答），不是盲信一个AI贴的标签

**技术风险集中在第1、2步**（概念提取+去重），这两步需要真实案例反复迭代提示词才能稳定，其余步骤是复用现有机制的成熟工程。

**用户提出的进阶方向（未成形，需要单独设计讨论，不要在开工前默认全都要做）：**

- **提取"用户自己的理解方式"而不是标准术语**：比如用户没记住"无为"这个词，但AI能从用户自己的对话措辞里提炼出用户真实的理解表达，用用户自己的话作为关键词标签——这会让第1步的提示词设计明显更复杂（不只是"提炼概念"，是"提炼+还原成用户自己的表达"）
- **技能树/科技树式的图谱交互**（游戏设计里的成熟模式，Duolingo等学习App也在用）：已掌握的概念是"点亮的星球"，还没连接的用虚线/半透明显示，暗示"可以往这个方向学"
- **链接预测（Link Prediction，图论里的成熟技术方向）**：AI根据现有图结构预测"还没连起来但很可能会连起来"的概念，主动推荐去读哪本书的哪部分能"融会贯通"，甚至一键跳转到阅读器对应位置或直接把上下文放进问AI输入框
- **文言文词汇掌握度追踪**：跟"概念理解"是完全不同的维度（一个是"懂多少字词"，一个是"懂多少思想"），用户自己也不确定该用图谱还是"笔记本"形式呈现，需要单独讨论，不要跟概念图谱混在一张图里
- **卡片式阅读**：文言文理解门槛高，现在"打开书翻页"这种阅读路径可能不适合，考虑分段做成卡片逐条阅读、每读完一张形成沉淀——这是阅读器UX的独立方向，跟知识图谱无关，不要混着讨论
- **多层级知识图谱+跨用户/跨AI生态API开放**（2026-08-06新提出，范围明显大于以上几条，单独说明）：现有图谱是单层扁平结构，用户设想改成"书籍自动分类（商业/历史/心理学等）→同类概念向上聚合成宏观节点→点进去看细分星球"的多层结构，并且希望未来能开放API让用户自己积累的知识图谱数据被外部AI访问使用。**决策层评估：这不是加功能，是几乎重新设计一遍**——分类逻辑、多层聚合的数据结构和提示词都要重新做；API开放给外部访问还涉及真实的用户数据隐私/安全问题（谁的数据、谁同意、怎么防滥用），这部分是需要专门讨论的产品决策，不是工程量问题。**明确不排期，需要单独一次设计讨论才能收窄范围，不能默认全都要做。**

**前提条件**：先做完"书架式"过渡结构（已完成）、简单版关联标注先稳定跑一段、积累真实使用反馈之后再评估要不要启动。范围很大，正式排期前需要专门再拉一次设计讨论把范围收窄，不能直接把这条备注当验收标准去开工。

### 预置书库支持"从我的书架隐藏"

2026-08-06用户提出：以后可能想让用户能把不喜欢的预置书从自己书架上移除，腾出空间导入自己喜欢的书。**这次决策层已经把"导入的书支持删除"派发出去（见`04-开发进度记录.md`同日记录），但预置书这条明确排除在外，用户自己也说"先不做，后续再讨论"。**

语义上这不是"删除"——预置书库是所有用户共享的，不能真删（会影响其他人）。要做的话本质是"从我的书架视图里隐藏"，需要给`books`表和用户之间加一张可见性/隐藏关联表，比这次"导入的书加`imported_by`字段"这种量级的改动更大，涉及书架查询逻辑的重新设计。**前提条件**：等这次"导入书删除"功能上线跑一段、观察真实使用情况后再评估要不要做，不要现在顺带做。

### PDF导入排版还原度：表格识别+图片提取（2026-08-06决策层拍板：认可要做，排在语音陪伴之后）

2026-08-06用户第一次提供真实PDF原文件测试后，真机反馈"排版和原文差距明显"，具体列了三类：①表格内容被拆散成乱序文字（PDF的表格没有"表格"这个结构概念，纯文字提取天然丢失网格关系）；②原文的图片完全缺失（现在的转换逻辑只提取文字，不处理图片）；③少量文字乱码（PDF内嵌字体编码解析限制，换提取库可能会好一点但不保证解决，这条不是逻辑bug，不属于这次的范围）。

**同一批真机反馈里另外两个问题（XHTML转义报错崩溃、页眉误判成章节导致内容被吞并/超大章节）已经确认是真bug并修复，跟这条要分开看——那两个不需要再讨论，这条才是需要决策层评估的新范围。**

技术现实：**"完全还原原文排版"和"字体大小可调/能划线"这两个目标互斥，不存在两者都要的方案**——PDF是固定坐标排版格式，要像素级还原本质上就是直接展示原始PDF，不转换成可重排版的格式；而阶段十五"转成EPUB复用现有阅读器基础设施"这个架构前提，本身就是用"放弃精确排版"换来的"可调字体+可划线+复用现有基础设施"，这是立项时就定的方向，不是这次才发现的取舍。

如果决策层评估后决定要往"表格/图片也保留"这个方向投入：
- 表格识别需要换用能分析文字坐标的库（比如`pdfplumber`）重新识别出表格网格，转成真正的HTML`<table>`，是一块新增功能，不是小改动
- 图片提取需要额外的版面分析逻辑判断"这张图该插入正文哪个位置"，同样是新增工作量
- 两者都做完，跟"完全跟原文一模一样"依然有距离——那个终点意味着放弃可调字体、退回展示原始PDF，等于推翻阶段十五的架构前提，是另一条路，不是"再多做一点"就能到达

**2026-08-06决策层拍板**：用户明确表态"技术上可行就该做，只是排期先后的问题"——决策层提醒过"不是自己写代码不代表没有成本"（工程时间/测试轮次/token开销都是真实成本），用户认可这一点但依然坚持要做。**结论：认可投入，但排在这次确认的头号优先级（阶段十七语音陪伴核心体验）之后，不是现在插队开工。** 投入到什么程度（只做表格还是表格+图片都做）等排到这个位置时再具体定验收标准。

### TTS朗读声音可选（相对优先级较高，成本可能较低）

2026-08-06用户提出：现在`/tts`用的Edge TTS默认声音（女声），希望用户能自选声音、调节语速。**决策层判断这个可能是这批新需求里性价比最高的一项**——项目已经在用的Edge TTS本身自带几十种免费、无版权限制的声音（不同性别/风格），技术上大概率只是加一个选择界面+把选中的voice ID传给已有接口，不需要新接入任何服务或换供应商，跟表格识别、知识图谱分层这类需要新写核心逻辑的功能不是一个量级的投入。**前提条件**：需要实际去核实Edge TTS的声音列表和调用方式细节（决策层这个判断基于对Edge TTS通用能力的了解，没有具体查过这个项目现在用的库版本支持到什么程度），核实后如果确认成本低，可以考虑跟阶段十七并行推进，不用等语音陪伴完全做完。

### 读书笔记精美化呈现 + 可选分享（跟"社交转型"提案是完全不同的两件事，需要划清界限）

2026-08-06用户提出：希望用户在读一本书过程中积累的划线/问答，能整理成一份比较精美的"专属笔记"（时间轴、可回溯当时的疑问），甚至可以整理成文章/书评选择性分享出去，认为这对用户有"社交价值"。

**需要明确记录的界限**：这跟同一天早些时候被决策层否决的"社交/婚恋匹配+送礼收费"转型提议（详见私有记忆，不在本项目共享文档中）是完全不同性质的想法——**这次说的是"用户自己数据的更好呈现方式+可选的导出/分享入口"，不需要匹配系统、不需要聊天室、不改变产品定位**，是常规backlog功能，不是产品定位转型。

**前提条件**：复用现有`highlights`/`qa_history`数据，是呈现层的新功能，不涉及新数据采集。排在阶段十七之后，无具体验收标准，需要前端设计阶段展开。

### 迁移到 Readium 原生渲染引擎

划线选字触控不灵敏，此前判断是`@epubjs-react-native`底层WebView文本选择机制的硬限制（250ms防抖+`selectionchange`事件时机不稳定），根治方案是换成Readium这类原生渲染引擎（不再依赖WebView的DOM选中事件）。**这不是新想法**，早在阶段一技术选型时就记录过"先用简单方案验证核心体验，真遇到卡顿再迁移"这条路径，现在可能到了要认真考虑的时候。

**前提条件**：这是大工程（需要跳出Expo Go托管流程，阅读器相关代码要重新做），不能顺带做。2026-07-2X用户发现《中庸》比《大学》选字成功率明显更低，说明可能还有内容/排版结构层面的具体因素——阶段十一先排查这个更便宜的可能性，只有排查结果确认是纯库层面通病、且用户量上来后反馈量确实很大，才启动这次迁移。
