### 具体任务清单（2026-09-23 用户口述，决策层整理并做过冲突排查）

**用户的原始诉求（听书朗读页）**：
1. 正文能整章连续上下滑动查看，不再只显示当前这一小段。
2. 朗读时手指不动的情况下，画面自动滚动，让正在念的那句**始终停在屏幕中间**。
3. 当前正在念的句子字号跟其它句子**一样大**，不要再有字号变化——这是修一个真实 bug：[`NarrationParagraph`](../../mobile/screens/ListenScreen.js) 里当前句的 `fontSize` 用 `Animated` 从 16.5 插值到 19.5，每换一句字号跳一次，用户反馈这会造成"眼睛失焦"。改成三档只用颜色/透明度区分（念过的最暗、正在念的最亮、还没念的中等），**这个三档颜色逻辑代码里已经有**（`opacity` 那组动画），只是要去掉 `emphasis`/`fontSize` 那组插值，不用重新设计配色。
4. 用户手指主动上滑离开当前朗读位置时，自动跟随滚动应该暂停；用户滑到自己想听的地方后，能有一个操作（点这句 / 一个悬浮播放键，你判断哪种手感更好，不确定就问决策层或用户）跳转播放位置到那一句，然后恢复自动跟随。

#### ⚠️ 冲突排查结论：分两阶段做，第二阶段要等

决策层查过代码和当前工作目录状态，结论：

- **第一阶段（现在就能做，跟其他人不冲突）**：上面第 1、2、3 点，都属于"怎么把文字显示出来、怎么自动滚动"，只涉及 `NarrationParagraph` 组件、`buildCaptionContext`（现在只截取当前段前后约180字的"小窗口"，要改成能支撑整章连续滚动的取法）、以及渲染这块的 JSX（`ListenScreen.js` 里 `captionScroll`/`captionScrollContent` 那一段，约在文件 2330～2345 行附近，行号仅供定位，以你实际读到的为准）。**不要动播放队列/TTS调度/位置保存逻辑**（`playFrom`、`paragraphProgressRef`、`resumeProgress` 相关函数），那不是这次要动的范围。
- **第二阶段（要等）**：上面第 4 点"滑到哪句点播放就跳去念哪句"。**这个功能需要一个"给定目标段落+段内字符位置，停止当前播放并从那里重新开始朗读"的能力**——而 Codex 侧 2 号工程师正在做的"听书隐私隔离/连续进度"任务（见本文件前面"已知背景"一节），核心也是同一件事：书重新打开时"从上次听书位置附近继续播放"。**两边如果各写一套，会做出两套不兼容的跳转逻辑，后面大概率冲突或要返工。**
  - **写这份任务卡时，2号（Codex）工作目录里已经有大量未提交的暂存改动**（`api/main.py`、`mobile/lib/api.js`、新文件 `mobile/lib/listenContinuity.js` 等），说明它正在实时推进这块，还没提交/推送。
  - 第二阶段**开工前必须**：`git fetch` 确认 2号（Codex）那份工作已经提交并推送到 `origin/main`，读一遍它新增的"跳转到某位置播放"函数（大概率在 `ListenScreen.js` 或新文件 `listenContinuity.js` 里），**复用它，不要自己另写一套**。如果迟迟没等到，回来问决策层，不要自己决定"等不及了先写一套"。

#### 施工边界（保证第一阶段不越界）

- 只改：`NarrationParagraph` 组件本身、`buildCaptionContext`（或替换成能取整章文本的新函数）、`captionScroll`/`captionScrollContent` 这段 JSX 及相关 `styles.caption*` 样式。
- 不改：`playFrom`、`paragraphProgressRef`、`resumeProgress`、任何跟 TTS 请求/音频队列/位置持久化有关的函数——这些是 2号（Codex）正在改的区域，你只需要读它们暴露出来的 `activeIndex`/`captionSentenceIndex` 之类的现成状态来驱动显示，不要重构它们。
- 施工前后都要 `git diff --stat` 自检一遍改动范围，确认没有超出上面这份清单；`git add` 时明确列出文件名，不要用 `git add -A`（工作目录里可能一直有别人的未提交改动）。
- 自动滚动要能"分辨用户是不是手动碰了屏幕"（用 `onScrollBeginDrag` 这类真实触摸事件，不要把代码自己触发的 `scrollTo` 误判成用户手动滑动），这是这个功能能不能用的关键，做完务必真机测试"边听边手动上滑"这个场景。
- 整章连续渲染要留意性能（长章节文字量可能不小），真机测一下滚动是否流畅，不确定要不要做"只渲染可见区域附近"这类优化，先做出来看效果再判断，不要一开始就过度设计。
