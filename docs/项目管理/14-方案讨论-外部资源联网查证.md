## 一、什么问题该联网，什么不该/不能联网

**应该触发**（满足其一即可，最终判断建议交给模型自己按提示词规则决定是否调用搜索工具，而不是另写一层独立的意图分类器——见第九节 MVP 的理由）：

- 问题指向书本之外的**现实世界事实**：作者生平/背景、书中提到的真实历史事件、书出版之后是否有新进展、书中引用的统计数据是否仍然准确。
- 用户话里带**时效性信号**："现在""最新""这几年""还有效吗"这类词。
- **高风险领域**（医疗/法律/政治/金融）且问题本身要现实事实而不是书中观点，比如"这本书说的这个药还在用吗"。

**不应该/不需要触发**：

- 关于书本身内容、情节、人物、写作手法的问题——这是"书内依据"该管的事，联网只会引入噪音，还可能把网上对这本书的二手解读当成原文，风险更高。
- 纯粹的文学开放讨论/象征意义解读——第一阶段已经加了"一种可能的理解是"这类开放解读规则，联网搜索在这里没有意义，还会让回答变机械。
- 用户自己的阅读记录/笔记类问题——这条链路是"用户记忆"，不是这次要做的"外部事实"，两者不要混。
- 触发但没有额度/被限流/用户关闭了联网功能时——直接跳过，不强行联网，按第六节降级。

## 二、三条证据链怎么分开

延续现有 `availableEvidenceType` 的命名习惯，不推倒重来，新增而不是替换：

| 证据链 | 对应现有/新增字段值 | 来源 | 现状 |
|---|---|---|---|
| 书内依据 | `current_context`（当前页/章）、`user_selection`（划线） | 阅读器实时读取 | ✅ 第一阶段已上线 |
| 用户记忆 | `conversation_memory` | 用户历史问答/笔记 | 评测集已预留坑位，**生产还没做**，不属于本次讨论范围 |
| 外部事实 | 新增 `external_fact`（或类似命名，最终由工程师定） | 搜索/内容抓取服务 | 本次讨论的主题，**目前完全不存在** |

**组装方式**：延续 `_prepare_ask` 现有的 `context_block` 拼接模式，外部查证结果作为独立的一段（类似现有【书名】【划选段落】那种【】标签块），不要混进书内正文那一块，让模型和后续的证据类型判断都能清楚区分"这段是书里的"还是"这段是网上查的"。提示词需要新增一条规则：**回答里如果用到了外部查证内容，必须让读者能分辨哪句话是书里的、哪句是查来的**，不能糅成一段分不清。

**2026-09-24补充澄清（常见误解）**：不管最终选博查还是千问的联网能力，**都不是把 DeepSeek 换掉**——`ChatBook` 跟用户对话的"大脑"始终是 DeepSeek，第一阶段针对它调好的安全边界、温度、苏格拉底流程完全不动。外部查证服务（不管哪家）只承担"去查资料、带回来带来源的原文片段"这一个子任务，查回来的结果作为新的一段证据块喂给 DeepSeek，由 DeepSeek 按现有规则组织语言回答用户。换成别的搜索服务商很轻量；换掉主模型是完全不同量级的工程，本方案不涉及、也不建议。

**顺带回答一个常见疑问**：DeepSeek、OpenAI、Claude 这些大模型API，为什么不能直接用它们"自己"的联网能力？——OpenAI 和 Claude 的 API 其实**真的有**联网搜索工具，但都是**单独收费、要显式打开**的（OpenAI 约每千次搜索10美元，另计网页内容token费），不是免费自动开启的；而且这两家都是海外服务，用它们等于把当初选 DeepSeek 就是为了避开的"国内访问限制"问题又绕回来。DeepSeek 本身确认没有这个能力。所以不管选哪条路线，"给国内可达的模型外接一个国内可达的搜索能力"都是必须自己做的事，不存在"其实早就有、我们没发现"这种情况。

**建议方向**：海外选项（Bing官方/Tavily/Serper）不是不能用，是还没有验证过国内可达性，真要选之前必须先实测，不建议优先考虑——这个项目已经在 Railway 身上吃过一次"国内用户访问海外服务器慢"的亏，没理由再引入类似风险。

**博查 vs 千问自带联网，2026-09-24更新**：查清楚价格后，**这两家价格和能力其实很接近**（千问约2.9分/次+2000次免费，博查约3～4分/次），不是一个明显更便宜。差别在别处：博查是单纯的搜索API，接入简单、不用管模型版本；千问联网是"模型自带能力"，要用阿里云原生的 DashScope 接口才能拿到可标注的具体来源。**建议不急着二选一，先各拿一点免费额度（千问有2000次免费），用第一阶段现成的评测框架实际跑几道测试题比一比，再决定选谁**，比现在纯靠资料判断更可靠。

## 四、来源可信度怎么分级，多个来源冲突怎么办

**简单三级分类，不做复杂的机器学习式打分**（复杂度换不来多少准确度提升）：

- **高**：政府/官方机构网站、书籍/作者官方页面、主流权威媒体、行业官方机构（如卫生健康部门）。
- **中**：主流新闻媒体、有一定知名度的专业网站。
- **低/不单独采信**：个人博客、论坛帖子、无法确认作者和日期的页面、明显的营销/SEO页面。

**具体怎么标注，2026-09-24补充**：不需要额外花钱调用 AI 去判断每条来源，用一份**我们自己维护的域名信任名单**（政府网站、官方机构、权威媒体、维基百科这类域名，写死在代码里）就能做——搜索结果回来后，程序自动核对每条结果的域名在不在名单里，命中就标"较可信"，没命中就标"来源未知，请自行判断"，纯代码规则，不产生额外 AI 调用成本。这套逻辑跟选哪家搜索服务无关，博查和千问（走 DashScope 原生接口时）都能拿到逐条带链接的结果，都能套用同一份标注逻辑。

**多源冲突处理**：

- 一般问题：如果排名靠前的几条结果观点不一致，**如实呈现两边说法+各自来源**，不要模型自己挑一个当标准答案。
- 高风险问题（医疗/法律/金融）：来源冲突或者没有"高"级别来源时，**直接走第七节的确定性安全前缀**，不尝试自己下结论。
- 时效性问题优先选**带明确日期**的结果，没有日期的老页面不采信为"最新"依据。

## 五、引用怎么展示，又不破坏阅读体验

- **正文答案本身保持现在的风格**（不用 Markdown、不用链接语法——这是现有 `SYSTEM_PROMPT` 就有的硬性格式要求，联网这块不应该破坏它）。
- 引用信息作为**独立的结构化字段**（类似现有 `availableEvidenceType` 那样挂在完成事件的元数据里），前端收到后渲染成答案下方一个可折叠的"查看来源"小条（标题+域名+日期），**不影响阅读时的文字流**，用户想核实才点开。
- **听书场景**：TTS 不朗读链接本身，可以在回答末尾一句话提示"这条信息来自网络查证，可以在文字记录里看来源"，把详细来源留在可视的对话记录里，不打断听觉体验。

## 六、超时、无结果、网页读不出来时怎么降级

- 严格遵守 `CLAUDE.md` 已经定的硬约束——**调用外部 API 用 `Promise.allSettled`，单个接口失败不影响整体**，这条早就是项目规矩，联网搜索直接照做。
- 搜索本身超时（建议给一个几秒级的硬上限，具体数值留给工程师结合真实延迟测出来定）或返回空结果：**回退成"用我了解的一般知识回答，并明确说明没有查到最新资料"**，标成 `general_knowledge`，不能装作查到了。
- 某条具体网页打不开/读不出正文：跳过这一条，用其它结果，不为了凑数编内容。
- 全部来源都不可用：诚实告诉用户"这个问题需要查证外部资料，但这次没能查到，建议你自己搜索确认"，不是每次都必须"查到点什么"才罢休。

## 七、医疗/政治/法律等高风险内容需要哪些额外保护

**复用第一阶段已经验证有效的模式，不另起一套**：第一阶段已经证明"只写进提示词让模型自觉"不够可靠（真实回归测出过模型只反问不给安全边界），最后是靠**确定性前缀**（不管模型怎么组织语言，先固定输出一段安全提示）才稳定住的。外部查证这块应该延续同一个思路：

- 高风险问题涉及外部查证时，**来源等级必须达到"高"，且不能互相矛盾**，否则强制走确定性安全前缀，不尝试给出确定性结论。
- **政治类内容建议第一版直接不做自动联网**，只保留"如果需要，人工可开启"的开关——这类内容除了事实准确性，还牵扯内容合规判断，我不是这方面的专家，不该由我在方案里替你拍板，建议你自己找懂政策合规的人确认要不要做、做到什么程度。
- 医疗/法律/金融：搜索结果只能作为"辅助读者进一步核实的线索"，不能替代"请咨询专业人士"这条底线——这条第一阶段已经写进确定性前缀了，联网只是多给一个可核实的来源，不改变这条底线。

## 八、怎么扩展现有固定评测集，验证"引用真的支持答案"

现有 42 题评测集已经是个成熟框架（六类、双 adapter、六维评分），建议**扩展而不是重建**：

1. **新增一类题**（比如叫"外部事实/时效性"），题目设计上刻意包含：① 有稳定权威来源可查证的事实类问题；② 故意设计"来源会冲突"的问题，检验模型是不是老实呈现分歧而不是硬选一边；③ 故意设计"查不到/服务超时"的场景（可以用 mock 掉搜索返回空结果来测），检验降级是否诚实。
2. **评分表加一维**：现有六维（依据准确性/事实正确性/诚实表达不确定/深度/清晰度/来源标注）里，`evidence_labeling`（来源标注）这一维可以直接扩展定义，把"有没有实际引用了正确来源"也纳入判断；也可以新增第七维专门叫"**引用有效性**"——0分=引用和答案对不上或者链接是编的，1分=有引用但没真正支撑关键结论，2分=引用确实支撑了给出的结论。具体要不要新增维度还是扩展现有维度，交给实际写评测的工程师判断，这里只给方向。
3. **这部分工作可以现在就开始、不用等选定搜索厂商**——设计题目和评分标准是厂商无关的，唯一要等的是"真实调用搜索 API"这一步。这也是一个低风险、可以先做的子任务。

## 九、三档方案：MVP / 正式版 / 长期版

> 时间和成本都是**量级估计**，不是精确排期——真正开工时要由认领的工程师结合实际情况重新估。

### MVP（最小可用）

- 只接一个国内搜索服务（建议博查，见第三节理由），只在提示词规则判断"确实需要外部事实"时才触发，不是每次 `insufficient_context` 都自动联网。
- 来源展示只做最基础版本：标题+链接+日期，前端一个可折叠条，不做复杂的可信度分级 UI（分级判断在后端做、体现在"要不要采信"上，前端先不用可视化展示等级）。
- 高风险问题：联网结果仅作参考，依旧强制走现有确定性安全前缀，不单独设计新逻辑。
- 评测：先加 5～10 道新题，验证"该触发的触发了、不该触发的没触发"这个边界，以及基础的引用展示，不追求覆盖所有冲突场景。
- **粗估工作量**：后端接入+触发逻辑+降级 3～5 人日，前端引用展示 1～2 人日，加真机验证 1～2 天，量级在**一周左右**，不是精确数字。
- **粗估成本**：按博查约¥0.035/次算，假设每天触发 N 次联网查询，月成本约 `N × 30 × 0.035` 元——这是占位公式，需要代入真实的日活/触发率数据才有意义，现在没有这个数据，不编一个假设的日活出来算。

### 正式版

- 补上多源比较+冲突呈现的完整逻辑，完整实现第四节的可信度分级。
- 评测集扩到 20～30 题，覆盖各类降级和冲突场景。
- 引用 UI 打磨（比如按可信度分级给来源加个小标记）。
- 视情况追加第二个搜索源做交叉验证，进一步降低"单一信源出错"的风险。

### 长期版

- 打通"书籍 RAG + 用户记忆 + 外部查证"三条链路，让模型自己判断该用哪条或者组合使用，而不是三条各自独立运作。
- 图片：这次讨论已确认要的是"搜索结果里带的配图"，不是 AI 生图（见 `12` 号讨论稿），这一步可以在长期阶段把图片结果字段接进来，技术上不难，但要一起考虑版权和展示方式。
- 如果要接海外信源（比如某些作者背景资料只有英文/海外网站有），需要专门评估访问稳定性和内容合规边界，这块我没有把握给出结论，需要你自己找懂行的人确认。

## 决定（2026-09-24，实测后拍板）

**选千问，不选博查。** 用产品负责人自己的账号，真实调用了两家的接口（各花了不到 2 毛钱/都在免费额度内），跑了 5 道真实问题做对比，结论很清楚：

- **拍板的关键证据**：问"《原则》作者瑞·达利欧现在还在管理桥水基金吗"和"桥水基金现在管理规模多大"这两道题，**博查翻到前 10 条结果依然全部文不对题**（搜出的是巴菲特、利物浦足球俱乐部老板去世之类完全无关的新闻）；千问同样的问题**搜到了 2025 年 8 月达利欧彻底退出桥水、现任 CEO 是谁这类很具体、很新的真实信息**，并带着可核实的新闻链接。
- **排除了"是总结环节的问题"这个干扰因素**：专门做了一次公平对比——把博查搜到的原始结果原样喂给 DeepSeek 自己总结，DeepSeek 的表现是诚实的（搜索结果不相关时会说"没查到"，不编），**证明瓶颈不在总结这一步，在博查的搜索检索本身这一步**。
- **样本量不大（5道题），不代表博查在所有问题类型上都不行**，理论上博查那边可以加一道"先把口语化问题改写成搜索关键词再搜"的工序来补救，但没有必要为了博查专门再加这一层复杂度——千问不需要这一步就搜得到。
- 千问的联网调用方式确定为：**走 DashScope 原生接口（不是 OpenAI 兼容接口），带上 `enable_search: true` 和 `search_options: {enable_source: true, enable_citation: true}`**，这样才能拿到逐条带链接的结构化来源列表，回答里也会自动带 `[1][2]` 这样的引用编号，不用我们自己另外解析。
- 千问搜到的来源里也混着知乎个人回答、雪球股民帖子这类不够权威的内容，**证明第四节"自己做域名信任名单"这一层依然必要，不因为选了千问就能省掉**。

**已生成的测试凭证**：产品负责人的阿里云百炼账号下已创建一个 API Key（描述"ChatBook 联网搜索质量测试"），博查账号也创建了一个但已确认弃用（不再需要）。**实现阶段建议新建一个描述清楚的正式 Key（比如"ChatBook生产环境-联网查证"），不要直接沿用这个测试用的**，测试 Key 可以之后在控制台删掉。具体任务见 `15-任务卡-外部查证MVP.md`。
