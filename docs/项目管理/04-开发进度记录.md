## 使用规则

1. 开始工作前，先读这份文件的最新记录，了解上一次做到哪、留了什么问题
2. 做完一段有意义的工作（不用每个小改动都记），补一条新记录
3. **区分"必须停下等用户回复"和"可以自己判断、边记录边继续"**（2026-07-11 修订，之前的规则太保守导致项目进度依赖用户实时在场，效率上不去）：
   - **必须真正停下等确认的**（这三类之外，不要停）：涉及花钱（增加付费服务/订阅）、可能造成数据丢失或不可逆操作、会推翻本项目文档里已经明确写下的架构决策
   - **可以自己判断、不用等回复就继续做的**：技术实现细节的取舍、方案是可逆的、影响范围局限在当前这一小块功能——用自己认为最合理的方案往下做，把"做了什么判断、为什么这么判断"写清楚记在这份记录里即可，不用等用户回复才继续。用户看到记录后不同意的话，随时可以叫停或要求返工，但不需要提前等批准再动手
4. 提交代码时，git commit message 里注明对应 WBS 的哪个阶段
5. **每个新阶段开工前，验收标准必须先写进 `05-验收标准.md`，缺验收标准不开工**（2026-07-14 新增——阶段四测试中发现整个项目此前从未定义过"做到什么程度算通过"，该缺口不允许再出现）
6. **需要用户拍板、或等用户提供东西（API密钥/账号/付费等）的事项，必须写进本日志——哪怕已经在对话里当面问过用户、甚至已得到口头答复**（2026-07-14 新增——用户同时与两侧实时对话，口头沟通不留痕会让另一侧决策层失明；写明事项+状态：待确认／口头已答复待落实／已解决。日志是唯一完整事实源）

## 开发经验法则（每次开工前必读；从下方时间线记录中提炼晋升而来）

> 晋升规则：时间线记录是日记，只写不删；但值得反复使用的教训要提炼成一条法则加进这里。
> 本区必须保持精简（10 条以内），过时的删掉——这里膨胀到没人读，等于没有。

1. **黑盒卡住、无报错 → 插桩，别猜**：第三方库莫名卡住又不报错时，直接在 `node_modules` 里的库源码插 `console.log`（Metro 会把真机日志转发回终端），比"猜测→改代码→让用户重试"的循环快得多（2026-07-14，真机调试三个bug的教训）
2. **改了 `node_modules` 必须 `patch-package` 持久化**，否则任何人重新 `npm install` 后坑原样复现（2026-07-14）
3. **合并到 main = 立刻部署生产**（Railway 自动部署），这两件事在本项目是一回事，合并前过一遍脑子（2026-07-11）
4. **多层 shell 转发（Git Bash→wsl.exe→bash）里变量插值会被外层提前展开**，测试命令写成脚本文件再执行，避免"鉴权失败"这类假警报（2026-07-14）
5. **外部数据源的结构假设必须实测，不能信"通常如此"**：EPUB"每章一个文件"、目录文件可用性，Gutenberg 全都不符合（2026-07-11，详见学习笔记03）
6. **验证要分层如实汇报**：验证到哪一层（本地/生产/web端/真机）就说哪一层，"代码逻辑对"和"真机上摸过"是两回事（2026-07-11 阶段三的实践）
7. **拿到真机反馈先查 `git log` 确认改动已部署，再动手分析问题**：mobile App 请求的是硬编码的生产环境地址，本地改了没提交推送=真机测的还是老代码，差点在错误的代码版本上排查半天（2026-07-21，苏格拉底提示词那轮的教训）
8. **"没报错、元素数量对"不等于"视觉上看得见"**：接入新UI库（图标/字体这类）光检查编译通过、DOM元素数量对不上没意义——`stroke`误写成`strokeWidth`同名参数那次，图标结构完整存在但颜色值非法、画不出线条，两种检查全部通过、图标却完全不可见。必须做一次实际截图/真机确认（2026-07-26，阶段十一Tabler Icons的教训）
9. **"完全没有任何报错"本身就是一条诊断信息，比"有报错但查不出所以然"更该警惕；同一个技术方案内部反复打补丁都失效时，别继续深挖同一条路线，先联网查这是不是已知问题、有没有验证过的开源解法。** 知识图谱黑屏问题在"零报错、纯黑屏"这个精确症状浮现之前，几轮排查一直在同一套react-native-svg+reanimated方案里打转（砍元素数量、修babel插件路径），每次都有理有据但都没解决——"零报错"这个具体现象指向问题出在reanimated worklet那条独立于主线程的执行环境里（主线程的错误处理系统看不见那条线程的异常），而"同一方案打了N轮补丁依然无效"这件事本身，才是真正该触发"跳出这个方案找完全不同技术路径"的信号，不是继续在里面猜下一处代码。最终解法（WebView+Canvas）不是猜出来的，是查证"这类复杂可视化用WebView渲染"是业内验证过的真实模式之后才定下来的（2026-07-30，阶段十二知识图谱黑屏，六轮debug后的教训）

## 手机真机连接怎么起（2026-08-06 更新：EAS Update 目前只覆盖安卓，iOS依然是隧道模式）

> **2026-08-06 2号员工(华为电脑)核实纠正**：下面这套EAS Update流程**只对安卓测试者生效**——`eas build:list`查过，目前只打过1个安卓包，iOS从来没有构建过。用户自己的真机是iPhone，装不了这个安卓包，覆盖不到。iOS要不要也上"直接装的正式App"这条路，需要用户在两个方案里拍板：**免费UDID方案（7天过期，比较麻烦）**或者**付费Apple Developer Program（$99/年，TestFlight，不过期）**——这是要花钱的决定，还没拍板，不要默认走付费路线。**在这个决定之前，iPhone端测试维持原样：Expo Go + 隧道模式**，由华为电脑那边挂着服务器，跟之前完全一样，什么都不用变。

**下面这套只对安卓测试者生效：两台开发机各自开发，都推到 `main`，谁想让安卓测试者测到自己的改动，就在自己那台机器上跑一次 `eas update --branch preview`（几十秒完成），已经装好的正式安卓APK（不是Expo Go）冷启动时会自动检测并拉取最新JS——不需要IP地址、不需要同WiFi、不会因为服务器重启打断正在进行的测试。**

具体步骤：
1. `mobile/` 目录下跑 `eas update --branch preview --message "简述这次改了什么"`
2. 告诉用户：完全关闭再重新打开App（不是切后台，是真正划掉杀进程），就能拿到最新版本
3. 这个方式**只对纯JS/业务逻辑改动生效**——如果改动涉及新增原生依赖、`app.json`里的图标/启动画面/权限这类原生配置，或升级Expo SDK版本，必须走`eas build`重新出包，OTA更新覆盖不到这些
4. 两台机器要都能推，运行`eas whoami`确认已经登录过有权限的Expo账号（`diegoxue`或团队账号），没登录过先`eas login`一次

**局域网/隧道模式的本地开发服务器依然保留，用在这些场景**：需要Metro的实时热更新做快速UI迭代、不想为了改一行代码就消耗一次EAS Update、或者需要用Expo Go测试（而不是测已装的正式APK）。启动方式：项目根目录跑 `.claude/launch.json` 里的 `mobile-lan` 配置（`npm --prefix mobile run lan`）。**不要用 `npx expo start`**——版本跟项目里锁定的不一致，会导致 Expo Go 报"无法连接"。查当前局域网IP用`ipconfig`（找"无线局域网适配器 WLAN"下的IPv4，不是以太网那个），把`exp://<IP>:8081`这行纯文字直接发给用户（不要生成二维码图片、不要用Artifact发链接——2026-07-23那次全部对用户失效过，只有纯文字稳定成功）。

**2026-08-06 新增约定——发链接必须标注是哪台机器（用户当面要求）**：排查语音识别问题时踩过一次坑——用户不确定自己手机当时连的是哪台开发机的服务器，导致怀疑的bug其实是"连了没拉最新代码的那台"，排查方向整个偏了。**以后每次把`exp://`链接发给用户，前面必须加"1号工程师（华硕电脑）"或"2号工程师（华为电脑）"这个文字标签**——App里显示的项目名字两边都一样（都是"沉光共读"），没法从App本身区分，只能靠这个文字标签让用户认。两边工程师都要遵守这条，不能省略。

**2026-08-06 补充——纯文字标签不够用，加了App内视觉角标**：用户反馈只在聊天里标注链接不够——他点开Expo Go之后，看到的项目列表/App内显示的名字两边完全一样，光靠"点哪个链接"记不住自己现在到底连的是哪台机器，验收到一半想确认都没地方看。改法：`App.js`新增`EngineerBadge`组件，读`process.env.EXPO_PUBLIC_ENGINEER_LABEL`这个`EXPO_PUBLIC_`前缀的环境变量，非空时在App右上角（登录页、加载页、主界面全覆盖）常驻显示一个红底小角标，直接写着"1号工程师（华硕电脑）"这类文字；不设这个变量时（包括所有正式EAS构建）完全不渲染，不影响生产。**变量不放`.claude/launch.json`或`package.json`里**——这两个文件是git共享的，两边机器的值不能一样，会互相覆盖。改放`mobile/.env.local`（已在`.gitignore`的`.env*.local`规则里，天然不会被提交/拉取覆盖），Expo内置支持自动加载。**两边工程师各自在自己机器的`mobile/.env.local`里写一行**：
```
EXPO_PUBLIC_ENGINEER_LABEL=1号工程师（华硕电脑）
```
（2号工程师/华为电脑改成对应文字即可）改完要重启`expo start`（Metro只在启动时读一次`.env.local`，光靠Fast Refresh不会生效）。文字标签的约定依然保留、不作废——两个手段一起用，链接标签帮用户"点对入口"，App内角标帮用户"进去之后随时能确认没连错"。

**2026-08-06 再补充——App内角标也不够，得在"点开之前"就能分辨**：用户马上指出角标方案的漏洞——角标是App内部的，得先点开、加载出界面才看得到；如果点错了，还得退出来重新选，体验上跟没有区分一样。用户明确要求：直接把标签拼进Expo Go项目列表/标题栏显示的App名字本身（形如"沉光共读（1号工程师）"），这样点开之前，在Expo Go的"最近打开"列表里就能选对，不用打开了才知道点错没错。

做法：`app.json`的`expo.name`是纯静态字段，没法读环境变量；改成新增`mobile/app.config.js`（Expo官方支持的"动态配置扩展静态配置"写法——两个文件同时存在时，Expo会把`app.json`解析出的内容当`config`参数传进`app.config.js`导出的函数里，函数返回值才是最终生效的配置）：

```js
module.exports = ({ config }) => {
  const label = process.env.EXPO_PUBLIC_ENGINEER_LABEL;
  if (label) config.name = `${config.name}（${label}）`;
  return config;
};
```

复用同一个`mobile/.env.local`里的`EXPO_PUBLIC_ENGINEER_LABEL`（改成短一点的"1号工程师"/"2号工程师"，不带"华硕电脑"这种括号里的括号，避免名字里出现嵌套括号），本地`expo start`时这个变量生效、名字变成"沉光共读（1号工程师）"；EAS正式构建的环境不设这个变量，`app.json`原样生效，生产App名字不受影响。验证方式：本地起`expo start --lan`后访问`http://localhost:8081`，页面`<title>`标签能看到带后缀的名字，跟Expo Go读到的manifest name是同一个字段，已确认生效。

### 历史：为什么 2026-07-23 曾经放弃过 EAS Update，现在为什么又捡回来

2026-07-23 遇到的问题是：**用 Expo Go 扫码/输入地址直接连开发中的项目**（不是本文档现在推荐的这种）时，报 `HTTP 403 signed-in Expo account does not have access to the account that owns this project`，试过公开项目/邀请成员都没解决，加上二维码图片交付当天全部失败，用户权衡后拍板放弃、改用本地服务器。

**2026-08-05 想清楚了：那次失败的是"Expo Go 直连开发项目"这条路，跟现在这条"给已经装好的正式APK推OTA更新"根本是两个不同的功能**，只是都挂在"EAS"这个品牌下容易混为一谈——`eas update`更新的是已安装的独立构建（`eas build`产出的APK/IPA），走的是`expo-updates`这个模块在冷启动时检查更新，不涉及Expo Go、不涉及"这个账号能不能访问这个开发项目"这个403报错的触发路径。这条路径今天（2026-08-05）在阅读器一揽子bug修复里已经连续用了5次以上，全部成功，没有复现过任何权限问题——**不是"问题被修好了"，是"这本来就是另一条不会触发那个问题的路径"，之前把两件事当成一件事，误判了。**

**接入难度：** 两家都是WebSocket协议的流式接口，都有官方Python SDK（腾讯云 [tencentcloud-speech-sdk-python](https://github.com/TencentCloud/tencentcloud-speech-sdk-python) 是开源的，阿里云是DashScope SDK），接入本身不复杂。账号层面只需要基础的实名认证（个人认证即可）——查证时发现一个容易误解的点：网上查到的"企业资质认证"要求，那个是外呼系统/400号码专属的运营商合规要求，跟纯语音转文字的ASR API无关，不适用于我们这个场景，不算接入门槛。

**⚠️ 关键架构洞察，比选哪家供应商更重要：** 现有的`/transcribe`接口是"完整录完一段→一次性上传→等转录结果"模式（一次性/非流式）。阿里云/腾讯云查到的这两个"实时语音识别"产品，本质是**流式**API——边录音边通过WebSocket发送音频片段，转录结果随说话实时返回，说完话那一刻转录基本已经完成，不用再等"上传+处理"这段串行等待。这意味着：

- 单纯把接口换成阿里云/腾讯云、但手机端录音逻辑还是"录完整段再传"，只能吃到"大厂通常没有冷启动、延迟更稳定"这一部分好处（预期能稳定在1秒左右，不会有类似SiliconFlow那样偶发8秒的情况），代码改动量接近"平替一个上传接口"
- 要吃到"实时"真正的速度优势，需要把手机端的录音方式也从"录完整段再传"改成"边录边用WebSocket发片段"——这是明显更大的架构改动（涉及`expo-av`录音API的用法、后端从REST接口改成WebSocket服务端点），工作量跟单纯换供应商不是一个量级

**结论/建议（给决策层参考，非拍板）：**
1. 如果目标只是解决"偶发卡顿"这个具体痛点，成本最低的路径反而是不换供应商——给SiliconFlow加一个定期"保活"请求防止模型被回收（阶段十已识别过这个选项），比接入新供应商改动小得多，缺点是会持续消耗调用额度（要花钱）
2. 如果决定要换供应商，腾讯云"大模型版"（≈1元/小时）性价比最高、且有现成开源Python SDK，最容易上手
3. 但如果不同时做"录音方式流式化"这个更大的改造，换供应商本身治标不治本——能治好"冷启动"，治不好"录完→上传→处理"这条串行延迟链路本身。要不要为了延迟体验去动这块更大的工程，需要决策层单独权衡，不是简单的"选哪家便宜"的问题。

## 2026-07-26（续）· 用户+华硕电脑的 Claude · 知识图谱三次重做：从"力导向平铺+2D平移"改成"3D球面旋转+恒星行星展开"

**用户反馈的三个问题，在效果图上依次解决：**

1. **"点会超出黑色画布边界"+"我想左右滑动的时候整个图谱像个星球一样转"**——原来的双指缩放/拖拽平移是纯2D变换叠在SVG外面，没做边界裁剪，缩放平移到某个位置节点会跑到画布外面看不见；且用户从一开始就明确要的是"星球"隐喻，不是平移。效果图第一版把整个交互模型换成真正的3D球面旋转（Fibonacci sphere均匀分布节点、绕Y轴/X轴双轴旋转投影、正面节点放大变亮/背面缩小变淡），画布本身用`overflow:hidden`裁死，边界问题不用额外处理就自然解决了。

2. **"双击之后全部展现出来但是什么都看不见，双击也不会精确居中"**——效果图第二版排查出两个独立的真bug：(a) 展开逻辑让所有159个节点同时可见，节点密度和"太挤看不清"的原始问题一样没解决；(b) 双击后的镜头居中计算只解了水平方向（rotY），完全没解垂直方向（rotX），纬度不在赤道上的节点必然偏移，纬度越极端偏得越狠——这是真正的数学错误，不是观感问题。

   处理：改成"恒星/行星"两层模型——用真实的关联边跑连通分量算法（union-find），每个分量里连接数最多的节点当"恒星"，其余当"行星"（零关联的孤立节点自己就是没有行星的恒星）。默认视图全部节点和边都画出来但行星画得很小很暗当背景纹理（这条是后面第4点里用户追加反馈才加的，见下），双击带光环的恒星才展开——行星被"拉"到恒星当前屏幕位置周围的一个固定环上（不是用它们各自原来在球面上的位置，那些位置离恒星可能很远），同时镜头转到正对着这颗恒星。居中计算重新推了一遍——水平方向解`rotY`（让节点单位向量的水平分量转到正前方），垂直方向再用这个结果解`rotX`（让垂直分量也归零）——用真实数据里纬度最极端（uy=1.0，球面顶点）的节点验证过，展开后像素级精确居中，不再是只解一半。

3. **"看不到总体连线，只能一颗一颗双击看"**——第一版"恒星/行星"实现里，没展开的行星连同它们的边一起被隐藏了，等于把全局关联这层信息藏起来。改成全部节点、全部边永远都渲染，只是没展开的行星和它牵的边画得很小很暗（当背景纹理），双击展开的那颗恒星的行星和边才变亮变大、貌似真实的"发现细节"体验。

## 2026-07-26（续）· 用户+华硕电脑的 Claude · 真机反馈：标签重叠+一滑动黑屏，两个都处理了

审查后认定最可疑的方向是**性能/负载，不是逻辑错误**——原来的实现里，每个节点的球面投影（`projectNode`，里面有正弦余弦运算）在星光点（Circle）、标签（Label）、光环（Halo）三个独立的`useAnimatedProps`里各自重新算一遍，一个带光环的恒星一次要算3遍投影；每条边的可见线和加宽命中区域也各自重新投影两个端点，等于4遍。159个节点+44条边，拖拽旋转时这些worklet每帧（理论60fps）全部要重新跑一遍——不确定这个计算量本身是不是真的会导致黑屏（没有profiler数据，无法100%确认因果），但这是真实存在的多余开销，砍掉不会有任何副作用，先处理掉是合理的第一步。

具体改法：用`useDerivedValue`把每个节点/每条边端点的投影结果只算一次，光环/标签/圆点三个`useAnimatedProps`和边的两条Line都从这同一份已经算好的结果里取字段用，不重新调用`projectNode`——原来最多要跑的投影次数直接砍掉约三分之二。顺手把`Gesture.Pan`/`Gesture.Pinch`的`.onUpdate`/`.onEnd`回调都显式加上了`'worklet'`指令（原来靠babel插件自动识别，理论上没问题，但显式声明成本是零、排除掉"回调没被正确worklet化"这一种可能性）。

**如实说明这次修复的置信度**：标签重叠这条，数字算得清楚、有把握是真正修复了。黑屏这条，只是"排查后认定最可疑的方向、把这个方向的多余开销清干净了"，**不是"确认过就是这个原因导致的"**——如果真机上还是会黑屏，说明根因是别的（比如`GestureDetector`跟大量`AnimatedCircle`/`AnimatedLine`原生`onPress`共存这个更底层的兼容性问题，`04-开发进度记录.md`上一条记录已经点名过这是从"双指缩放"那版开始就存在、一直没被验证过的已知风险点），需要用户描述得更具体一点（黑屏是完全黑还是能看到星空背景？是整个App黑屏还是只有图谱区域？黑屏后App还能不能用返回键退出？）才能继续往下查。

## 2026-07-26（续）· 用户+华硕电脑的 Claude · 黑屏问题补充截图，缩小了范围+又修了一处真实开销

好消息先记一笔：用户反馈"问题，但也不是没问题"——翻译过来是黑屏已经不再出现了，上一条记录的两处修复（投影去重+worklet闭包剥离sources大文本）看起来是真的解决了黑屏问题。剩下两个反馈：转动的时候很卡、标签还是一次性显示太多。

**"卡"——这次真的抓到一个确定性的、不是靠猜的性能问题：** `projectNode`（球面投影用的三角函数）里的`cos(rotY)`/`sin(rotY)`/`cos(rotX)`/`sin(rotX)`这四个值，只跟镜头当前转到哪个角度有关，跟具体是哪个节点完全无关——但之前的代码写法是每个节点自己的投影worklet都独立重新算一遍这四个值，159个节点+边的端点，拖拽旋转时（理论60fps）每一帧要重复跑好几百次三角函数运算，且都是完全一样的结果、白算的。改成这四个值每帧只在最外层（`ConceptGraph`组件本身）算一次，包成一个`trig`共享值往下传，所有节点和边的投影都从这一份里取，不再各自重算。

顺带砍了另一块开销：漂浮动效原来119颗恒星+40个行星全部各自挂一个独立的`withRepeat`动画时钟（不管当前看不看得见都在跑），改成只给恒星开——行星本来就画得很小很暗当背景纹理，这份漂浮肉眼基本看不出来，但省下40个常驻的动画时钟。

**如实说明局限性：** 这两处优化都是真实存在、有把握的性能问题，砍掉之后拖拽应该会顺一些，但**没把话说满**——`react-native-svg`本身是"保留模式"的DOM式渲染，不是为"每帧同时更新几百个元素的位置"这种用法设计的，这是这套技术选型天生的一个性能天花板，不是靠优化几个具体的计算点就能完全消除的。如果这次改完拖拽还是有明显卡顿，下一步真正意义上的解法是把渲染层从`react-native-svg`换成`@shopify/react-native-skia`这类GPU加速的即时模式画布——但这是一次新增原生依赖（这个项目之前明确因为原生模块版本对不上吃过真机崩溃的亏，一直优先避开这类依赖），值不值得为这个功能单独破例，这个判断应该留给决策层，不是我自己悄悄就换了架构。这次先做完全不需要新依赖、风险最低的这两处优化，等用户真机反馈这版够不够用，不够用再正式讨论要不要上Skia。

**下一步：** 等真机反馈这版拖拽手感、标签数量是否可以接受。如果还是卡，需要就"要不要引入react-native-skia"这个架构级决定跟用户认真讨论一次，不能默认展开。

## 2026-07-27 · 用户+华硕电脑的 Claude · 黑屏其实一直没修好，这次换了个思路：统一触摸系统

**这次换了判断方向：** 两轮性能优化都没解决，说明黑屏大概率不是"算得太慢"，是结构性的——图谱里同时活着两套触摸系统：单击节点/连线走的是`react-native-svg`自己的原生`onPress`（基于旧的responder机制），双击/拖拽/缩放走的是`react-native-gesture-handler`的`GestureDetector`（新的手势识别系统）。这两套系统同时作用在同一批SVG元素上，是社区里公认容易互相冲突的组合——这个风险点从"双指缩放"那一版（阶段十二第二次改版）开始就在历次记录里反复提到过"已知风险、没有被验证"，一直没有真正处理，这次是第一次真正动手解决它。

**处理：** 把单击也从"react-native-svg原生onPress"改成走手势库——新增`Gesture.Tap().maxDuration(250)`当单击手势，命中测试逻辑扩展成`hitTestAllWorklet`（先测节点、再测连线，连线的命中用点到线段距离公式`distToSegmentWorklet`），命中结果通过`runOnJS`桥回JS线程调用普通函数打开对应的详情弹窗。`GraphNodeGroup`的圆点、`GraphEdge`的连线不再挂任何原生`onPress`——`GraphEdge`因此也不再需要额外一条"加宽透明命中线"，直接精简掉一整个SVG元素。全部触摸交互（单击/双击/拖拽/缩放）现在统一走同一套`GestureDetector`识别，SVG元素本身不再参与任何触摸判定，两套系统同时抢同一批元素这个可能性从根上被排除掉了。顺手把`GestureDetector`原来直接包`<Svg>`的写法改成包一层普通`<View>`（Svg作为View的子元素）——更常规、更保守的写法，虽然没有直接证据证明原来直接包Svg有问题，但改起来没有额外成本，一并做了。

**如实说明：** 这是目前为止对黑屏问题最有信心的一次修复——因为它是基于"排除了性能假设"这个真实证据推出来的下一个最可疑方向，不是又一次单纯的代码审查猜测。但依然要说清楚：**没能在本环境验证**（浏览器预览工具从始至终都没能进到这个页面），如果这次真机上还是黑屏，说明连"两套触摸系统冲突"这个假设也是错的，需要退回到"必须拿到真机的原生崩溃日志/JS报错信息才能继续"这条路——纯代码审查这条路径的边际收益已经不大了。

**下一步：** 等真机反馈。如果这次真的解决了黑屏，再回头看拖拽是否够顺滑、标签数量是否合适；如果依然黑屏，需要用户想办法拿到真机的错误日志（摇一摇手机开Expo Go开发菜单看Logs，或者找一台能连Xcode/Android Studio的设备接上看原生崩溃栈）。

## 2026-07-27（续）· 用户+华硕电脑的 Claude · 停下来讲清根因 + 决策层选方案A + 实施

**给用户讲清的根因（决策层对话，不写代码）：** 159个节点全部同时渲染、一直都在，每个节点1-3个SVG元素（圆点+标签+可能的光环），加上边，算下来同时约300-380个独立SVG元素活在屏幕上，拖拽时每一个都要每帧重算位置。底层`react-native-svg`是保留模式（类似网页DOM，每个元素都是单独追踪的原生对象、单独更新推屏）——画静态图或几十个动画没问题，但"每秒60次、同时挪动300多个元素"这种用法是它天生的结构性天花板。之前几轮针对"算得更聪明"的优化（trig去重、闭包瘦身）没用，正是因为瓶颈从来不是算得慢，是原生元素数量本身太多。"一显示就一堆节点"和"卡"是同一个根源的两副面孔——调暗一个行星不等于不渲染它，它照样每帧参与计算。给了两条路：**方案A**（减少同时挂载的元素，不换技术，中等改动、无新依赖）、**方案B**（换`@shopify/react-native-skia`即时模式GPU画布，教科书级正解，但新增原生依赖，跟本项目一贯"能不加原生依赖就不加"冲突）。建议先A后B。

## 2026-07-30 · 用户+华硕电脑的 Claude · 知识图谱黑屏问题：六次重做，换成WebView+Canvas彻底绕开根因

## 2026-08-06（续）· 1号员工(华硕电脑) · 语音识别真机反馈一揽子排查，真根因是腾讯云账户欠费

- 自动重试3次（虽然这次是欠费导致，但"连接被服务端意外中断"这个故障模式未来仍可能因为真实的瞬时网络问题出现，重试代价很低）

## 2026-08-06（续七）· 2号员工(Claude Code) · 用户终于给了真实PDF：揪出两个真bug + 一个必须由决策层拍板的技术权衡

1. **XHTML转义bug（这才是用户截图里那个报错的真根因）**：`_build_epub_from_sections`把提取出的文字原样塞进`<p>`/`<h1>`标签，没做HTML转义。扫过这本书完整提取文本（9.8万字），`&`出现1次、`<`出现3次、`>`出现7次——都是真实存在的（引用文献"Keynes & ..."、数学公式"a > 0"这类）。用`html.escape()`转义后，写测试专门验证含`&/</>`的文本能生成合法XHTML，之前会崩现在不会了。

2. **页眉误判成章节标题，导致重复章节+超大章节两个连带问题**：真实PDF里"前言""后记"这类运行页眉每页都重复出现（"前言 3""前言 1"这种，只有页码不同），原来的识别逻辑把每次出现都当成新章节起点——不仅制造出重复的"前言"假章节，还因为真正的"第1章"到"第4章"没能被规则识别出来（这本书的章节标题在PDF提取后没有形成规则能命中的独立短行，规则本身有局限，如实说明），导致"后记"和"前言"之间几万字的真实正文全部被吞成一个巨型"章节"（实测354个段落挤在一起）。**两处修复**：①识别到的标题先按"去掉末尾页码后的主体文字"去重，连续重复只保留第一次出现（真正的章节起点），后面的重复当成同一章内的页眉噪音；②任何一个最终章节如果字数超过`_MAX_CHAPTER_CHARS`（约7500字），二次按`FALLBACK_CHAPTER_CHARS`切分成"标题 (1)"/"标题 (2)"这样的子节，不会再出现一个大到没法读的章节。用这份真实PDF实测：从"5个章节（含3个重复的前言/后记假章节）"变成"31个章节，每个大小合理"。

**如实说明局限：** 这本书真正的"第1章"到"第4章"这几个有意义的标题，这次修复后依然没能被正确识别出来（章节内容还在，只是被归到"后记 (N)"这种技术性标签下，不是"第一章 ..."这种有意义的标题）——PDF提取后这几处标题跟页码/正文粘连的具体方式，用当前的正则规则识别不出来，需要更多真实样本才能调出更可靠的规则，这次没有为了"看起来解决了"就继续在这一个文件上反复调参数拟合，容易过拟合到这一本书。

**关于用户提出的核心问题（能不能做到跟原文排版一模一样、保留表格和图片）——这是一个需要决策层拍板的架构级权衡，没有自己决定，如实说明技术现实：**

1. **"完全还原原文排版"和"字体大小可调"这两个目标在技术上是互斥的**——PDF是固定排版格式（每个字符钉死在页面上的坐标），要做到像素级还原原文，本质上就是把原始PDF直接拿来当PDF显示，而不是转成EPUB这种"可以重新排版"的格式。反过来，字体大小能调、划线能选字，前提正是文字变成了可以重新流动排版的HTML，这种转换天然会丢失原始的精确视觉布局——两者只能选一个方向，不存在"两个都要、都不牺牲"的方案。
2. **表格**：PDF里的表格没有"表格"这个结构化概念，只是若干文字按坐标摆成网格——纯文本提取（现在的`pypdf.extract_text()`）会完全丢失这个网格关系，表格内容原样变成一坨乱序文字，这正是用户截图里表格乱码的原因。技术上可以做（用`pdfplumber`这类库分析文字坐标重新识别出表格网格，转成真正的HTML`<table>`），但是一块新增的、有真实工作量的功能，不是这次顺手改的范围。
3. **图片**：现在的转换只提取文字，完全没有处理图片。技术上`pypdf`能把PDF里嵌入的图片提取出来，但"这张图应该插入在正文哪个位置"需要额外的版面分析逻辑，也是新增工作量。
4. **部分文字乱码（比如截图里表格数字变成一堆冒号句号）**：这次查证是PDF内嵌字体的编码问题（`pypdf`的字符映射解析不了这本书某些字体子集），不是逻辑bug，换`pdfplumber`这类库可能会好一些但不保证——这是文本提取库本身的已知局限，不是靠改动这次的代码逻辑能保证解决的。

**给决策层的问题，需要拍板方向**：现在的架构选择是"牺牲精确排版和表格/图片，换取可调字体+可划线+复用现有阅读器基础设施"——这是阶段十五立项时就定下的方向（"不新建PDF渲染引擎，复用现有阅读器基础设施"）。如果要往"表格/图片也保留"这个方向投入，工作量不小（结构化表格识别+图文混排），且离"完全跟原文一模一样"依然有距离（那需要放弃可调字体、退回展示原始PDF，等于推翻阶段十五的架构前提）。需要用户/决策层明确：这次真机反馈暴露的问题里，哪些是"必须现在修的bug"（如实说，这次已经修的两个属于这类，不需要再问），哪些是"愿意投入更多工作量换取更好效果的新功能"（表格/图片支持，需要决策层评估投入产出比再排期）。

**下一步：** 提交推送这次修的两个真bug，部署后用同一份《人口与日本经济》PDF重新导入验证（这次终于有原始文件可以真实对比效果，不用再靠合成数据），效果应该比用户截图里那版好不少（至少不会再有XHTML崩溃报错、不会再有重复的"前言"假章节、不会再有一个几万字的巨型章节），但表格/图片/剩余的少量乱码依然会存在，如实说明清楚不要让用户以为这次修完就是"跟原文一模一样"了。
