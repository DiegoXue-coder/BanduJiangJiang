## 开发经验法则（每次开工前必读；从下方时间线记录中提炼晋升而来）

> 晋升规则：时间线记录是日记，只写不删；但值得反复使用的教训要提炼成一条法则加进这里。
> 本区必须保持精简（10 条以内），过时的删掉——这里膨胀到没人读，等于没有。

1. **黑盒卡住、无报错 → 插桩，别猜**：第三方库莫名卡住又不报错时，直接在 `node_modules` 里的库源码插 `console.log`（Metro 会把真机日志转发回终端），比"猜测→改代码→让用户重试"的循环快得多（2026-07-14，真机调试三个bug的教训）
2. **改了 `node_modules` 必须 `patch-package` 持久化**，否则任何人重新 `npm install` 后坑原样复现（2026-07-14）
3. **合并到 main = 立刻部署生产**（Railway 自动部署），这两件事在本项目是一回事，合并前过一遍脑子（2026-07-11）
4. **多层 shell 转发（Git Bash→wsl.exe→bash）里变量插值会被外层提前展开**，测试命令写成脚本文件再执行，避免"鉴权失败"这类假警报（2026-07-14）
5. **外部数据源的结构假设必须实测，不能信"通常如此"**：EPUB"每章一个文件"、目录文件可用性，Gutenberg 全都不符合（2026-07-11，详见学习笔记03）
6. **验证要分层如实汇报**：验证到哪一层（本地/生产/web端/真机）就说哪一层，"代码逻辑对"和"真机上摸过"是两回事（2026-07-11 阶段三的实践）
7. **拿到真机反馈先查 `git log` 确认改动已部署，再动手分析问题**：mobile App 请求的是硬编码的生产环境地址，本地改了没提交推送=真机测的还是老代码，差点在错误的代码版本上排查半天（2026-07-21，苏格拉底提示词那轮的教训）

## 手机真机连接怎么起（每次新会话/换网络都要走一遍）

> 新对话/新设备打开这个项目、需要真机测试时，直接照这个流程操作，不用重新摸索。
> **2026-07-23 用户当面拍板：固定只用下面这一种方法，不要再尝试 EAS Update 云端方案、
> 不要发二维码图片**——原因见文末"已废弃"说明，走了一整天弯路才定下来的，别再走回头路。

1. **启动开发服务器**：项目根目录跑 `.claude/launch.json` 里的 `mobile-lan` 配置（本质是 `npm --prefix mobile run lan`，等价于 `mobile/` 目录下 `npm run lan` = `expo start --lan`）。**不要用 `npx expo start`**——版本跟项目里锁定的不一致，会导致 Expo Go 报"无法连接"。
2. **必须用局域网模式，不用隧道模式**：`npm run tunnel` 在国内网络下经常连不上 `exp.direct` 这个域名（哪怕电脑本身有 VPN/Tailscale 能正常上网，也不代表隧道服务能连通），只在局域网模式完全不可用时才退回去试。
3. **前提**：手机和电脑必须连同一个 WiFi（不能用手机流量）。换了网络（换 WiFi、回家/换地方）之后，电脑的局域网 IP 会变，要重新走第4步查一遍。
4. **查电脑当前局域网 IP**：`ipconfig`，找"无线局域网适配器 WLAN"下面的 IPv4 地址（不是以太网那个）。
5. **把 `exp://<IP>:8081` 这行纯文字直接发给用户**——**不要**生成二维码图片、**不要**用 Artifact 发链接、**不要**用对话内嵌组件（`show_widget`）。这三种"发图片/发链接"的方式 2026-07-23 当天全部对用户失效（`SendUserFile` 工具当次会话中途被禁用、Artifact 网页链接用户那边一直加载不出来、内嵌组件也没能渲染出来），只有纯文字稳定成功。**只有 IP 真的变了才需要重新发**——服务器重启但 IP 没变的话，旧地址直接复用。
6. **告诉用户怎么连**：打开手机 **Safari**（不是 Expo Go App 本身）→ 地址栏粘贴这行 `exp://` 文字 → 回车 → iOS 会自动弹出"是否用 Expo Go 打开"，确认即可。这一步不需要 Expo Go 自带"手动输入网址"这个入口（用户反馈他手机上那个版本没有这个入口），是利用 iOS 系统级的 URL scheme 跳转，实测有效。
7. **验证服务器活着**：`curl http://<IP>:8081/status`，200 就说明没问题。
8. 这个开发服务器是当前会话/沙箱进程的产物，**换一个新对话或沙箱重启后进程会没掉**，需要重新走第1步启动，其余步骤视 IP 是否变化决定要不要重做。

## 2026-07-26（续）· 用户+华硕电脑的 Claude · ASR服务商调研结论（阿里云/腾讯云 vs 现用SiliconFlow）

**背景：** 阶段十当时排查过"语音识别7秒延迟"，结论是SiliconFlow SenseVoiceSmall模型冷启动导致（首次调用8.0秒，热身后1.3-1.6秒），不是我们代码的问题，当时没继续往下做（要不要加定期"保活"请求防止模型被回收，会持续消耗调用额度，是要花钱的决定，留给用户）。这次任务是查阿里云/腾讯云这两家能不能作为替代方案，只出结论，不动代码不花钱。

**价格对比**（均查证于官方最新计费文档，2026-07-26）：

| | 后付费起价 | 阶梯最低价(5000h+/日) | 免费额度 | 预付费最低 |
|---|---|---|---|---|
| 现用 SiliconFlow SenseVoiceSmall | 免费 | — | 无限（免费模型） | — |
| 阿里云智能语音交互(ISI) | 3.50元/小时 | 1.20元/小时 | 新用户免费试用3个月 | 30h/100元起，10000h/15000元(1.5元/h) |
| 腾讯云语音识别(ASR)基础版 | 3.20元/小时 | 1.20元/小时 | 每月5小时 | 30h/90元起 |
| 腾讯云语音识别 大模型版(BigModel) | 0.017元/分钟≈1.02元/小时 | — | — | — |

腾讯云"大模型版"单价明显低于两家的传统版本，是三个付费选项里性价比最高的。

**接入难度：** 两家都是WebSocket协议的流式接口，都有官方Python SDK（腾讯云 [tencentcloud-speech-sdk-python](https://github.com/TencentCloud/tencentcloud-speech-sdk-python) 是开源的，阿里云是DashScope SDK），接入本身不复杂。账号层面只需要基础的实名认证（个人认证即可）——查证时发现一个容易误解的点：网上查到的"企业资质认证"要求，那个是外呼系统/400号码专属的运营商合规要求，跟纯语音转文字的ASR API无关，不适用于我们这个场景，不算接入门槛。

**⚠️ 关键架构洞察，比选哪家供应商更重要：** 现有的`/transcribe`接口是"完整录完一段→一次性上传→等转录结果"模式（一次性/非流式）。阿里云/腾讯云查到的这两个"实时语音识别"产品，本质是**流式**API——边录音边通过WebSocket发送音频片段，转录结果随说话实时返回，说完话那一刻转录基本已经完成，不用再等"上传+处理"这段串行等待。这意味着：

- 单纯把接口换成阿里云/腾讯云、但手机端录音逻辑还是"录完整段再传"，只能吃到"大厂通常没有冷启动、延迟更稳定"这一部分好处（预期能稳定在1秒左右，不会有类似SiliconFlow那样偶发8秒的情况），代码改动量接近"平替一个上传接口"
- 要吃到"实时"真正的速度优势，需要把手机端的录音方式也从"录完整段再传"改成"边录边用WebSocket发片段"——这是明显更大的架构改动（涉及`expo-av`录音API的用法、后端从REST接口改成WebSocket服务端点），工作量跟单纯换供应商不是一个量级

**结论/建议（给决策层参考，非拍板）：**
1. 如果目标只是解决"偶发卡顿"这个具体痛点，成本最低的路径反而是不换供应商——给SiliconFlow加一个定期"保活"请求防止模型被回收（阶段十已识别过这个选项），比接入新供应商改动小得多，缺点是会持续消耗调用额度（要花钱）
2. 如果决定要换供应商，腾讯云"大模型版"（≈1元/小时）性价比最高、且有现成开源Python SDK，最容易上手
3. 但如果不同时做"录音方式流式化"这个更大的改造，换供应商本身治标不治本——能治好"冷启动"，治不好"录完→上传→处理"这条串行延迟链路本身。要不要为了延迟体验去动这块更大的工程，需要决策层单独权衡，不是简单的"选哪家便宜"的问题。

Sources: [阿里云实时语音识别计费](https://help.aliyun.com/zh/isi/product-overview/billing-10)、[腾讯云语音识别计费](https://cloud.tencent.com/document/product/1093/35686)、[腾讯云语音SDK GitHub](https://github.com/TencentCloud/tencentcloud-speech-sdk-python)

## 2026-07-26（续）· 用户+华硕电脑的 Claude · 知识图谱三次重做：从"力导向平铺+2D平移"改成"3D球面旋转+恒星行星展开"

用户对"力导向平铺+双指缩放平移"这版继续给反馈，指出三个具体问题，没有直接改代码，先用一个独立HTML/Canvas效果图（不碰真实App代码，本地起静态服务器、写程序化脚本模拟拖拽/双击/缩放测过，反复迭代了四版）跟用户来回确认，最后拍板定稿，再照定稿版本改真实RN代码——这个"先出效果图、真人确认过手感再动工"的流程是用户在这轮反馈里主动提出的方式，比"改代码→截图→用户反馈→再改代码"的老流程快得多，尤其是在这个会话浏览器预览工具持续不稳定、没法可靠地在RN app里试手势的情况下。

**用户反馈的三个问题，在效果图上依次解决：**

1. **"点会超出黑色画布边界"+"我想左右滑动的时候整个图谱像个星球一样转"**——原来的双指缩放/拖拽平移是纯2D变换叠在SVG外面，没做边界裁剪，缩放平移到某个位置节点会跑到画布外面看不见；且用户从一开始就明确要的是"星球"隐喻，不是平移。效果图第一版把整个交互模型换成真正的3D球面旋转（Fibonacci sphere均匀分布节点、绕Y轴/X轴双轴旋转投影、正面节点放大变亮/背面缩小变淡），画布本身用`overflow:hidden`裁死，边界问题不用额外处理就自然解决了。

2. **"双击之后全部展现出来但是什么都看不见，双击也不会精确居中"**——效果图第二版排查出两个独立的真bug：(a) 展开逻辑让所有159个节点同时可见，节点密度和"太挤看不清"的原始问题一样没解决；(b) 双击后的镜头居中计算只解了水平方向（rotY），完全没解垂直方向（rotX），纬度不在赤道上的节点必然偏移，纬度越极端偏得越狠——这是真正的数学错误，不是观感问题。

   处理：改成"恒星/行星"两层模型——用真实的关联边跑连通分量算法（union-find），每个分量里连接数最多的节点当"恒星"，其余当"行星"（零关联的孤立节点自己就是没有行星的恒星）。默认视图全部节点和边都画出来但行星画得很小很暗当背景纹理（这条是后面第4点里用户追加反馈才加的，见下），双击带光环的恒星才展开——行星被"拉"到恒星当前屏幕位置周围的一个固定环上（不是用它们各自原来在球面上的位置，那些位置离恒星可能很远），同时镜头转到正对着这颗恒星。居中计算重新推了一遍——水平方向解`rotY`（让节点单位向量的水平分量转到正前方），垂直方向再用这个结果解`rotX`（让垂直分量也归零）——用真实数据里纬度最极端（uy=1.0，球面顶点）的节点验证过，展开后像素级精确居中，不再是只解一半。

3. **"看不到总体连线，只能一颗一颗双击看"**——第一版"恒星/行星"实现里，没展开的行星连同它们的边一起被隐藏了，等于把全局关联这层信息藏起来。改成全部节点、全部边永远都渲染，只是没展开的行星和它牵的边画得很小很暗（当背景纹理），双击展开的那颗恒星的行星和边才变亮变大、貌似真实的"发现细节"体验。

**用户后续追问"节点少的时候会怎样"，顺手查了真实数据：** 当前159个概念节点里，只有48个来源100%对得上真实的划线/问答记录（前一条记录里查过的同一批测试数据污染问题，还没决定要不要清理），这48个真实概念之间只有5条真实关联边、4个带行星的恒星——这次没有编造演示数据，直接把这个真实子集也做进了效果图当第二个可切换数据集，让用户直观看清理后大概会是什么样子（大部分节点会是零关联的孤单恒星，图会明显空旷很多）。

**用户确认定稿后，正式改了生产代码（`mobile/components/ConceptGraph.js`，一次接近整体重写）：**

- 彻底去掉`d3-force`依赖（`npm uninstall d3-force`，`package.json`/`package-lock.json`一并清理）——球面投影是纯三角函数数学，不需要力导向布局库了
- 节点位置计算（球面投影、行星环绕展开、独立漂浮偏移）全部写成`'worklet'`函数，在UI线程用`react-native-reanimated`的`useAnimatedProps`跑，跟手势共享变量（`rotY`/`rotX`/`zoom`/`focusedStarId`）直接读写，不过JS线程——拖拽旋转要求连续60fps更新，走JS桥会卡，这是从"双指缩放+2D平移"那版就已经确立的技术方向，这次延续

## 2026-07-26（续）· 用户+华硕电脑的 Claude · 真机反馈：标签重叠+一滑动黑屏，两个都处理了

用户真机截图（球面默认视图）：几十个恒星的中文标签同时挂出来、字挤在一起完全看不清；另外反馈"一滑动就黑屏"。

**标签重叠——查到了确切原因，是数字算错了，不是运气不好：** 标签显示门槛是`depth>0.55`，159个节点里119个是恒星。均匀分布在球面上的点，`depth>k`这个条件对应的是球面上一块"炮弹头"形的面积，占比是`(1-k)/2`——k=0.55时占比22.5%，119颗恒星里同时有大约27颗正对镜头、同时挂标签，27个中文标签挤在一个手机屏幕宽的圆形画布里，截图里那种糊成一片完全是必然结果，不是转到了一个特别倒霉的角度。改成`depth>0.86`，同样算法算出来同一时刻大概只有4-6颗恒星挂标签，人眼能一个个看清楚。展开的行星（走环绕分支，`depth`被`projectNode`强制记成1）不受这个新门槛影响，永远清楚可读，不受影响。

**"一滑动就黑屏"——没能在这个会话里复现（浏览器预览工具这次又没能进到知识图谱页面，跟之前记录的持续性环境问题一样），只能靠代码审查排查，如实说明这次是"降低风险的加固"而不是"确认修复"：**

审查后认定最可疑的方向是**性能/负载，不是逻辑错误**——原来的实现里，每个节点的球面投影（`projectNode`，里面有正弦余弦运算）在星光点（Circle）、标签（Label）、光环（Halo）三个独立的`useAnimatedProps`里各自重新算一遍，一个带光环的恒星一次要算3遍投影；每条边的可见线和加宽命中区域也各自重新投影两个端点，等于4遍。159个节点+44条边，拖拽旋转时这些worklet每帧（理论60fps）全部要重新跑一遍——不确定这个计算量本身是不是真的会导致黑屏（没有profiler数据，无法100%确认因果），但这是真实存在的多余开销，砍掉不会有任何副作用，先处理掉是合理的第一步。

具体改法：用`useDerivedValue`把每个节点/每条边端点的投影结果只算一次，光环/标签/圆点三个`useAnimatedProps`和边的两条Line都从这同一份已经算好的结果里取字段用，不重新调用`projectNode`——原来最多要跑的投影次数直接砍掉约三分之二。顺手把`Gesture.Pan`/`Gesture.Pinch`的`.onUpdate`/`.onEnd`回调都显式加上了`'worklet'`指令（原来靠babel插件自动识别，理论上没问题，但显式声明成本是零、排除掉"回调没被正确worklet化"这一种可能性）。

**如实说明这次修复的置信度**：标签重叠这条，数字算得清楚、有把握是真正修复了。黑屏这条，只是"排查后认定最可疑的方向、把这个方向的多余开销清干净了"，**不是"确认过就是这个原因导致的"**——如果真机上还是会黑屏，说明根因是别的（比如`GestureDetector`跟大量`AnimatedCircle`/`AnimatedLine`原生`onPress`共存这个更底层的兼容性问题，`04-开发进度记录.md`上一条记录已经点名过这是从"双指缩放"那版开始就存在、一直没被验证过的已知风险点），需要用户描述得更具体一点（黑屏是完全黑还是能看到星空背景？是整个App黑屏还是只有图谱区域？黑屏后App还能不能用返回键退出？）才能继续往下查。

**下一步：** 等真机确认标签是否清楚了、黑屏是否还会出现。如果黑屏依然出现，需要用户提供上面这几个更具体的细节，或者（如果方便的话）用Xcode/Android Studio连着真机看有没有原生层面的崩溃日志——这个信息在这个纯软件会话环境里拿不到，只能靠用户那边直接看。

## 2026-07-26（续）· 用户+华硕电脑的 Claude · 黑屏问题补充截图，缩小了范围+又修了一处真实开销

用户补了一张"黑屏"实际截图：头部标题栏、tab栏、底部导航全部正常渲染，`知识图谱`这个tab本身也是选中高亮状态，星空背景的装饰星点也画出来了——**不是整个App卡死/崩溃**，是"图谱区域挂载成功但节点/连线/标签完全不可见"，比单纯的"崩溃黑屏"范围小很多，也更容易查。

顺着这个线索重新审查代码，发现一个之前没意识到的真实问题：`prepareGraph`准备出来的节点对象，除了投影要用的字段（size/category/球面坐标/恒星行星分级），**还完整带着后端返回的原始`sources`数组**——每个节点最多几条来源，每条来源里是完整的划线原文+AI生成的解释，加起来是不小的一段中文文本。这份带着全部原文的节点对象被直接传进了每个节点自己的`useDerivedValue`、以及双击手势的命中测试`hitTestWorklet`——这些都是要被reanimated"shareable化"、整份复制到UI线程自己运行环境里的闭包变量，159个节点各自带着完整来源文本反复被复制，是真实存在、之前没有意识到的开销，跟上一条记录里已经处理的"投影算3遍"是两个不同性质的问题（那个是重复计算，这个是重复搬运大量数据）。

处理：`prepareGraph`现在分别产出两份数据——精简版（只留id/label/size/category+算出来的球面坐标和分级信息，不带`sources`）给投影/手势这一层的worklet用；完整版（`fullById`，带完整`sources`）单独留着，只在点击节点/连线弹详情弹窗这个JS线程的回调里查一次，不会被搬进任何worklet闭包。点节点原来直接把节点对象传给`onPressNode`，现在改成只传`id`，弹窗那边用`id`去`fullById`里查完整数据——两层数据不会搞混。

**如实说明**：跟上一条记录一样，这次也没能在本环境复现"黑屏"（没能进到知识图谱页面），这是"看到用户截图后重新审出来的一个具体、真实存在的问题，合理怀疑是根因之一"，不是"确认修好了"。已经过语法检查、Metro整体打包无报错。

**下一步：** 等用户拿这版重新测。如果还是"星空背景在、图谱内容不可见"这个现象，说明还有别的原因，下一步该做的是让用户想办法看一眼真机上有没有JS层面的报错弹窗/日志（比如摇一摇手机在Expo Go里唤出开发菜单看Logs，或者问一下华为那边有没有装Android Studio能接真机看logcat）——纯靠这边猜代码的边际收益已经很低了，需要真实的错误信息才能继续精确定位。

## 2026-07-26（续）· 用户+华硕电脑的 Claude · 黑屏解决了，反馈变成"卡"+标签还是太多

好消息先记一笔：用户反馈"问题，但也不是没问题"——翻译过来是黑屏已经不再出现了，上一条记录的两处修复（投影去重+worklet闭包剥离sources大文本）看起来是真的解决了黑屏问题。剩下两个反馈：转动的时候很卡、标签还是一次性显示太多。

**标签太多：** `depth>0.86`那次调整不够狠——粗算过0.86对应约7%的球面正面积，119颗恒星里同时约8-9颗挂标签，对手机这么窄的画布还是太挤。这次提到`0.94`（约3%面积，同一时刻大概3-4颗），只有最靠近正中心的恒星才挂标签，其余恒星本身还在（能看到点、能点开），只是没显示文字——双击转到正中间之后单独那颗还是能看清楚。

**"卡"——这次真的抓到一个确定性的、不是靠猜的性能问题：** `projectNode`（球面投影用的三角函数）里的`cos(rotY)`/`sin(rotY)`/`cos(rotX)`/`sin(rotX)`这四个值，只跟镜头当前转到哪个角度有关，跟具体是哪个节点完全无关——但之前的代码写法是每个节点自己的投影worklet都独立重新算一遍这四个值，159个节点+边的端点，拖拽旋转时（理论60fps）每一帧要重复跑好几百次三角函数运算，且都是完全一样的结果、白算的。改成这四个值每帧只在最外层（`ConceptGraph`组件本身）算一次，包成一个`trig`共享值往下传，所有节点和边的投影都从这一份里取，不再各自重算。

顺带砍了另一块开销：漂浮动效原来119颗恒星+40个行星全部各自挂一个独立的`withRepeat`动画时钟（不管当前看不看得见都在跑），改成只给恒星开——行星本来就画得很小很暗当背景纹理，这份漂浮肉眼基本看不出来，但省下40个常驻的动画时钟。

**如实说明局限性：** 这两处优化都是真实存在、有把握的性能问题，砍掉之后拖拽应该会顺一些，但**没把话说满**——`react-native-svg`本身是"保留模式"的DOM式渲染，不是为"每帧同时更新几百个元素的位置"这种用法设计的，这是这套技术选型天生的一个性能天花板，不是靠优化几个具体的计算点就能完全消除的。如果这次改完拖拽还是有明显卡顿，下一步真正意义上的解法是把渲染层从`react-native-svg`换成`@shopify/react-native-skia`这类GPU加速的即时模式画布——但这是一次新增原生依赖（这个项目之前明确因为原生模块版本对不上吃过真机崩溃的亏，一直优先避开这类依赖），值不值得为这个功能单独破例，这个判断应该留给决策层，不是我自己悄悄就换了架构。这次先做完全不需要新依赖、风险最低的这两处优化，等用户真机反馈这版够不够用，不够用再正式讨论要不要上Skia。

**下一步：** 等真机反馈这版拖拽手感、标签数量是否可以接受。如果还是卡，需要就"要不要引入react-native-skia"这个架构级决定跟用户认真讨论一次，不能默认展开。

## 2026-07-27（续）· 用户+华硕电脑的 Claude · 停下来讲清根因 + 决策层选方案A + 实施

**如实说明置信度和局限（这次尤其要说清，因为用户成本敏感、且这是第N轮）：**

## 2026-08-04（续三）· 用户+华硕电脑的 Claude（决策层） · "语音陪伴核心体验"范围讨论 + 给1号员工的新指令：先做全双工音频技术验证，别直接开工全量功能

**结论一：不算被大厂实时语音模型（豆包/千问）覆盖，护城河判断成立。** 这套"持续讲解+开口打断+问是否继续+讲完沉淀理解"的交互，核心资产是"客观、苏格拉底式、不讨好"这个内容层设计（跟`05-验收标准.md`里"讲解模式暂时不动"是同一件事的语音化延伸），不是"能不能实时说话"这个技术层能力。大厂的实时语音模型解决的是后者，不覆盖前者。**这条不需要1号员工做任何事，只是确认方向没错。**

**结论二：因为阶段十五把所有书统一转EPUB、复用同一套阅读器基础设施，"语音陪伴"只需要针对EPUB阅读器建一次，不用区分"预置书"还是"导入的书"。** 1号员工做这块时，不用为"是否是导入的书"写任何特殊分支逻辑。

**结论三（重要，跟上一条记录里正在做的腾讯云切换是同一条技术路线，互相印证）：查证到腾讯云"大模型版"（0.017元/分钟≈1元/小时）确认是支持真正流式的产品，不是只能一次性识别**（[腾讯云语音识别计费文档](https://cloud.tencent.com/document/product/1093/35686)）。对比标准版流式识别3.2元/小时，大模型版便宜约3倍。这意味着：上面正在做的"腾讯云切换"不需要因为这次讨论推翻或重做——同一个供应商、同一个产品，既能服务现有的"点按钮问一句"场景，未来也能服务流式场景，两条线是兼容的，不是重复投入。

**结论四（这次讨论最大的新发现，是接下来给1号员工的实际指令）：全双工音频（边播AI朗读、边录用户说话）需要"回声消除"（AEC），否则麦克风会把手机自己在播的朗读声也录进去，导致误触发或识别混乱——这是语音助手类产品的经典难题，不是我们独有的坑。查证到**Expo默认的录音API不提供AEC能力**，需要引入新的原生模块（如`expo-two-way-audio`）才能拿到系统级AEC（[参考](https://sweets.chat/blog/article/implementing-offline-echo-cancelled-audio-in-expo-react-native)）。这正好是本项目反复踩过的雷区——新增原生依赖是这个项目历史上最大的不确定性来源（Reanimated版本冲突真机崩溃、图谱功能六次重做），这次是**音频这个全新的原生依赖类别，项目里从没用过，没有经验值参考**。

**决策层+用户拍板：不直接全量投入建这个功能，先做一次小范围技术验证（spike），验证通过再正式立项。**
