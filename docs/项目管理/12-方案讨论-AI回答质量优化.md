# 方案讨论稿：AI 回答质量优化（真实性 / 丰富性 / 角色感）

> 2026-09-23，用户与决策层（Claude Code）讨论产出。**这是讨论稿，不是已拍板的任务卡**——还没定优先级、没定派给谁，用户打算先自己想想，也打算拿去问 Codex 侧的意见。Codex 侧读到这份文件，欢迎直接在文末"Codex 侧意见"那节写自己的判断，不用另开文件。

## 背景

用户提出想优化"AI 问答"的整体质量，拆成三个维度：**真实性**（不能瞎编）、**丰富性**（延伸内容能不能查得到时效性信息）、**角色感**（AI 的人设/语气）。决策层读了 `api/main.py` 里问答相关的全部代码（`_prepare_ask`/`_build_ask_messages`/`SYSTEM_PROMPT`/`_socratic_system_prompt`），并核对了移动端三个发起提问的地方（`BookChatScreen.js`/`ReaderChatScreen.js`/`ListenScreen.js`），得出以下结论。

## 一、代码里查到的真实情况（真实性问题的根源）

### 1. `pageText`（当前页正文）在所有生产代码路径里都是空字符串——这是一个真 bug

- `mobile/screens/BookChatScreen.js:404`、`mobile/screens/ListenScreen.js:2108`、`2333` 三处发起 `/ask`、`/ask/stream` 请求时，`pageText` 全部写死传 `''`。
- 后端 `api/main.py:2564-2565` 确实写了"没有划线就退回用当前页正文"的兜底逻辑（`elif ctx.pageText: context_block += ...[:800]`），**但因为前端从不传，这条分支永远不会被触发**。
- **听书页不算真空**：`ListenScreen.js` 的两处提问把"当前正在念的这段文字"当作 `selection` 传了过去（`currentCaption`/`capturedText`），所以听书时 AI 是有原文可看的。**真正的缺口在阅读页的"问 AI"面板**（`BookChatScreen.js`）——用户不先划线选中文字，AI 就完全看不到当前页/当前章在讲什么。
- `mobile/screens/ReaderChatScreen.js` 是**死代码**，没有被任何地方引用/接入导航，不用管它。

### 2. 没有任何"书内容"的检索机制（RAG 素材完全缺失）

- 数据库里有三张表带向量检索能力：`qa_history`（历史问答）、`highlights`（用户划线）、`concepts`（知识图谱概念）——**没有一张是"书的正文分段"**。
- 也就是说，就算想做"按问题检索最相关的原文段落"，现在**连素材库都不存在**，不是"检索逻辑没写"，是"连能检索的数据都没准备"。
- 好消息：书的章节/段落拆分数据在导入时已经生成过（`standard_chapters` 表，用于阅读器/听书渲染），**理论上可以复用这批已经切好的段落，只需要额外算一遍 embedding 存起来**，不用从头设计切分逻辑。

### 3. 系统提示词（`SYSTEM_PROMPT`）没有任何"不许编"的约束

- 现有提示词只规定了语气、字数、格式（不用 Markdown/emoji），**没有一句要求"只根据给你的内容回答""不确定就承认不确定""不要编造原文引用"**。
- 直接讲解模式的 `temperature=1.0`（`_build_ask_messages` 里 else 分支），偏高，更容易"自由发挥"。苏格拉底模式是 `0.3`，相对保守。

## 二、丰富性问题：现在是 0 基建，不是"哪里没配对"

- DeepSeek 的 API **支持工具调用（function calling）**，V4-Flash（现在用的这个）和 V4-Pro 都支持，但**没有自带的联网搜索**，需要开发者自己接一个搜索服务、自己写"模型决定要不要调用搜索"这层逻辑。来源：[DeepSeek 官方文档](https://api-docs.deepseek.com/guides/tool_calls/)。
- 现在代码里调用 DeepSeek 时**完全没有传 `tools` 参数**（`api/main.py:2606` 附近），这套机制一次都没被用过。
- 国内可用、不用担心访问限制的搜索 API 举例：**博查（Bocha）**，专门面向 AI 应用做的搜索接口，国内合规。来源：[博查相关介绍](https://blog.csdn.net/m0_68233023/article/details/145533577)。这只是查到的一个例子，不是已经决定要用它。

## 三、角色感问题

- 不管在读哪本书，AI 用的都是同一段"亲切的读书陪伴助手"人设，没有按书调整语气。
- **苏格拉底模式的对话流程设计是真正花了心思的**（怎么判断用户是卡住求助还是在试探性回答、怎么识别"用户在吐槽对话本身"这种元评论），这块不是问题，值得保留，不建议大改。

## 四、DeepSeek 模型能力核查（回答"能不能支撑这套长期设想"）

查证时间：2026-09-23。以下信息会随时间变化，之后要用时建议重新查一次确认没过期。

| 能力 | DeepSeek 现状 | 来源 |
|---|---|---|
| 做 RAG（检索增强） | ✅ 支持，本质跟模型无关，只要能聊天就能用 | — |
| 工具调用（用来接搜索） | ✅ V4-Flash 和 V4-Pro 都支持 `tools`/`tool_choice` | [DeepSeek 文档](https://api-docs.deepseek.com/guides/tool_calls/) |
| 看懂图片（图片输入） | ✅ 2026年8月底已并入主力 Flash 模型，价格不变 | [DeepSeek 官方博客](https://api-docs.deepseek.com/news/news260821/) |
| 自己生成图片 | ❌ 不支持，且**本次讨论已确认不需要**——用户明确要的是"搜索引擎返回的配图"，不是"AI 现画一张"，所以这项能力用不上，不用另接画图模型 | — |
| 上下文窗口 | V4-Pro 查到约 100 万 token；V4-Flash 具体数字没查到，但同架构家族，通常也相当大——一本书正文一般几十万字，理论上塞得下，但出于成本和速度，仍建议走"检索相关片段"而不是整本塞进去 | [OpenRouter](https://openrouter.ai/deepseek/deepseek-v4-pro) |

**结论：三步都能在 DeepSeek 这一个模型上做完，不需要为了这个长期设想额外引入别的大模型，不违反 CLAUDE.md"用 DeepSeek 避开海外模型限制"这条硬约束。**

## 六、已经讨论确认的点

1. 第三步的"图片形式"，明确是**搜索引擎返回的配图**，不是 AI 自己生成图片——省掉了接画图 API 这条线。
2. 检索增强（第二步）的定位是"精准检索相关片段"，不是"把整本书塞进上下文"，理由是省钱省时间，不是技术做不到。
3. 决策层建议：**第一步现在就做（成本低、直接影响用户对产品的第一印象）；第二、三步建议放到10月公测之后**，避免跟"10天内阅读器/听书要交公测"这两个进行中的任务抢工程师时间。**这一条用户还没有最终拍板**，正是这份讨论稿要拿去跟 Codex 侧商量的地方。

### 总体判断

原“三步走”方向基本正确，但需要把问题拆成四层，避免把“联网搜索”等同于“真实性”：

1. **当前阅读依据**：AI 是否真正拿到了用户正在读的正文。
2. **整本书依据**：AI 是否能从全书检索相关段落（书籍 RAG）。
3. **用户记忆**：AI 是否记得这位用户在本书及跨书阅读中形成的目标、问题和沉淀。
4. **外部查证**：对时效性或高风险问题，AI 是否能使用外部权威来源并明确标注。

### 对原方案的修正

- 修复 `pageText` 是必要条件，但不能简单把整章全文塞进去。本轮应传“当前可见正文 + 前后相邻段落 + 书名/章节/位置”，保证相关且可控。
- 提示词里的“不许编造”只能改善行为，不能替代证据。回答需要保留明确的依据类型，后续 UI 可展示“依据当前页 / 本书 / 你的笔记 / 外部资料 / 一般知识”。
- 直接回答模式降低温度可以减少随机发挥，但不是事实保证；必须配合固定评测集比较前后效果。
- 轻量书籍 RAG 试验应在更大范围公测前完成，而不是全部推迟到公测后。完整上线可以后置，先用 20～30 本不同结构和题材的书验证召回与引用。
- 用户记忆应排在外部搜索之前。ChatBook 的差异化首先是“理解这本书并逐渐理解这个人”，不是变成一个通用搜索框。
- 外部搜索只在“查证 / 最新信息 / 书外延伸”等明确意图下触发；医疗、法律、政治、金融等高风险主题必须显示来源与日期，无可靠来源时不得给出确定结论。
- 不为每本书自动更换夸张人设。保留稳定的产品人格，通过“陪读 / 苏格拉底 / 研究 / 批判阅读”和“简洁 / 深入”控制工作方式。

### 调整后的实施顺序

1. **评测基线**：固定问题集、自动记录结果、人工评分表。
2. **当前上下文与证据规则**：修正文传递、提示词、随机性和依据元数据。
3. **轻量书籍 RAG 试验**：正文切块、检索、精确回到章节/段落，先小范围验证。
4. **结构化用户记忆**：会话级、书籍级、跨书级分层，且用户可查看、修改、删除。
5. **外部搜索**：最后接入，设置触发条件、权威来源策略、引用与失败降级。
