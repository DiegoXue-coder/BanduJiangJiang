# 上线分发方案评估

> 这份文档是给决策层开会用的——汇总"怎么把产品初步开放给别人用"这个问题目前调研到的全部结论，末尾列出需要决策层拍板的具体问题。不是执行文档，执行层面的任务分解等决策层讨论完再补进 WBS。

## 背景

产品准备做初步用户测试（体验版），核心要求是"不管用户在国内还是国外都要能用"。围绕这个目标做了三块调研（TestFlight 原生分发 / PWA 网页版 / Railway 后端国内可达性），过程中又验证出一条"今天就能用、成本最低"的临时分发方式，验证完之后发现了一个更根本的前置问题——**当前系统是单租户的，分发给第二个人就会跟用户自己的数据混在一起**。这份文档把这几条线索汇总起来，供决策层判断下一步先做什么。

---

## 一、三条正式分发路径的调研结论

### 1. TestFlight（iOS 原生分发）

**结论：代码/配置基本就绪，但有两处必须补的硬性缺失，且从未真正跑过一次 EAS Build。**

- 已就绪：App 图标 1024×1024（符合 App Store 要求）、EAS 项目已注册、`eas.json` 三档 build 配置已就位、麦克风权限说明文案已写
- 缺失（不需要付费开发者账号就能补）：
  1. `app.json` 里 `ios.bundleIdentifier` 完全没设置——没有它 `eas build --platform ios` 直接跑不起来
  2. 隐私清单（`expo.ios.privacyManifests`）没配置——苹果 2024 年 5 月起强制要求，不补会被 App Store Connect 直接拒收
- 真正的未知数：这个项目至今只在 Expo Go 里跑过，**从未执行过一次真正的 `eas build`**。这个项目之前吃过原生依赖版本不匹配导致真机崩溃的亏（reanimated/worklets 那次），EAS Build 是完全独立于 Expo Go 的原生编译环境，不能假设"Expo Go 里能跑 = EAS Build 能编译成功"
- **建议**：先补 bundleIdentifier，跑一次免费的 EAS Build（不需要买苹果开发者账号，只是编译出 .ipa），把"能不能编译成功"和"要不要花 $99/年买开发者账号"这两个决定分开验证，不要在同一步骤里承担两个未知数

### 2. PWA（网页版）

**结论：不是"能不能用"的问题，是要为两个核心功能单独重写一遍——真实工作量是 1-3 周级别的子项目，不是配置调整。**

逐项查证（不是假设）：

| 功能 | 现状 | 网页端支持情况 |
|---|---|---|
| EPUB 阅读器 | 依赖 `react-native-webview` | **官方明确不支持网页端**，社区有替代包但没有证据显示跟当前用的阅读器库组合有人验证过 |
| 语音输入（STT录音） | 依赖 `expo-av` | **官方文档明确网页端不支持录音**（该库本身也在被废弃）需要用浏览器原生 API 完全重写 |
| 语音播放（TTS） | 依赖 `expo-av` | 支持，风险低 |
| 字体（思源宋黑体） | 靠改 node_modules 源码的补丁 | 补丁对网页端无效，但网页端有更简单的原生方案（CSS 一行搞定），不算阻塞 |
| 图标库 | `@tabler/icons-react-native` | 支持，本会话已在浏览器预览里亲眼验证过 |
| 拖拽手势（知识图谱） | gesture-handler + reanimated | 官方声称支持，本会话未能在浏览器环境里完整验证复杂手势的实际效果 |

阅读器和语音输入是产品最核心的两个体验，这两块目前都没有现成能直接用的网页方案。

### 3. Railway 后端国内可达性

**结论：查不到"确定被墙"的证据，但有两个独立的、跟 GFW 无关也几乎确定成立的隐患，需要真人在国内实测才能拿到确切结论。**

- 服务器实际位置：查证 `bandujiangjiang-production.up.railway.app` 解析在 Railway 自有网络（AS400940），物理机房在美国旧金山——2024 年后 Railway 已把生产流量从 Google Cloud 完全迁出，自建机房，没有任何面向亚太/中国的边缘节点证据
- 隐患一：物理距离带来的延迟是确定会发生的，哪怕完全不被拦截，跨境往返延迟大概率在 200-400ms 甚至更高
- 隐患二：Railway 2026 年被曝出多起全球性的延迟/边缘路由问题（跟中国无关，但说明其全球路由本身不够成熟，走国内这条路线撞上类似问题的概率不低）
- **建议验证方法**：找一位在国内正常网络环境（不挂VPN）的人，直接访问 `https://bandujiangjiang-production.up.railway.app/health`，能不能打开、要等多久，一步到位确认现状
- 关联历史决定：2026-07-14 曾经把"国内网络可达性/ICP备案"这个问题记录为"v1 自用测试阶段不需要处理，等真要对国内用户开放时再处理"——如果这次"初步用户测试"确实要覆盖国内用户，这条记录里写的触发条件已经成立

## 二、已验证：今天能用的临时分发方式（不是正式方案）

**Expo Go + 隧道模式（tunnel）**，本会话已实际跑通并验证（公网链接返回 HTTP 200）：

- 原理：把开发服务器通过隧道暴露到公网，对方装免费的 Expo Go App，打开一个 `exp://` 链接就能直接运行当前这份代码，不需要跟你在同一个 WiFi
- 成本：零花费，零新增打包步骤，之后往 EAS Build/TestFlight 走是同一份代码的自然延伸，不是另起炉灶
- 限制：**运行这个服务的电脑必须保持开机、服务保持运行**，对方测试期间才连得上——这是临时借用开发环境，不是正式发布
- 国内可达性：跟上面第三条是同一类问题，隧道服务走的也是国际中转，国内用户能不能稳定连上没有把握，可以顺带用它测一下

**这条路径本身没问题，但用之前发现了一个更根本的前置问题（见下）。**

## 三、新发现的关键前置问题：多租户

分发给超过一个人使用之前，必须先确认这件事：**当前系统是单租户的，所有人的数据会混在一起，不是"性能扛不扛得住并发"的问题，是"数据会不会串"的问题。**

具体依据（已查证代码，不是猜测）：后端 `api/main.py` 里 `APP_USER_ID = 1` 是硬编码的全局常量，几乎每一个 `/app/*` 接口（书架、划线、问答、知识图谱……）的每一条数据库查询都用这个写死的值做归属判断。鉴权也不是"识别是谁"，是一把所有人共用的 HMAC 密钥（嵌在 App 安装包里，谁装了这个 App 谁就是"合法的同一个用户"）。也就是说：如果同时有两个人用这个 App，他们的划线、问答记录、知识图谱会被系统当成同一个人的数据混在一起，互相看得见对方的内容，无法区分。

要支持真正意义上的多人独立使用，大致需要（方向性列举，不是设计稿）：
- 一套真正的账号体系（注册/登录，取代现在"共享一把钥匙"的鉴权方式）
- 数据库层面把所有表里硬编码的 `user_id` 改成真正按登录用户动态区分
- 需要一并处理的关联决定：`03-风险登记表.md` 里已经记录过一条相关的硬性触发条件——"EPUB 下载接口的 token 走 URL 参数"这个已知的技术妥协，写明了"开放多用户注册之前必须改成短效专用 token"，这两件事阈值是绑在一起的，不能只做账号体系、不管这条

这块工作量不小，且是产品架构层面的决定（要不要现在做、做到什么程度），需要决策层拍板范围，不适合我单方面动手。

## 四、基础设施安排：迁移到 24 小时运行的服务器

用户已经决定：正式分发（不是今天这种临时隧道测试）不会长期占用当前这台电脑（华硕），会迁移到"华为服务器"那台设备上运行，实现服务 24 小时常驻、不受个人电脑开关机影响。

这一步需要提前确认（等真要迁移的时候再落实，先记录意图）：
- 华为那台设备是否已经有能跑 Expo/Node 开发服务器的环境（Node.js、npm、Expo CLI），还是需要重新搭建
- 华为那台设备此前的角色主要是跑后端 API 阶段的工作（见 `04-开发进度记录.md` 早期记录），没有运行过 mobile 端的服务，这次是新的用途，需要单独验证一遍"手机连华为电脑跑的 Expo 服务"这条链路是否走得通（同 WiFi 才能用局域网模式，隧道模式则不受此限但国内可达性未知，见上文）

## 五、需要决策层拍板的具体问题

1. **初步测试范围**：这次"体验版"打算覆盖几个人、国内国外都要有还是先挑一边？这直接决定 Railway 国内可达性这条要不要现在就解决
2. **多租户要不要现在做**：如果计划的测试人数超过 1 人，多租户是硬性前置条件还是可以先接受"大家共用一个账号、划线会混"这个妥协跑一轮定性反馈？
3. **TestFlight 还是继续用隧道模式**：如果决定要做多租户，是不是同时值得先把 bundleIdentifier/隐私清单这两处缺失补上、跑一次 EAS Build，为后续过渡到更正式的分发方式做准备？
4. **PWA 要不要现在启动**：鉴于阅读器和语音输入都要重写、真实工作量是 1-3 周级别，这个方向是否值得在"体验版"阶段投入，还是推迟到确认产品方向之后再做？
5. **华为服务器迁移的时间点**：是现在就着手确认环境、提前铺路，还是等多租户等前置问题定下来之后再迁移？
