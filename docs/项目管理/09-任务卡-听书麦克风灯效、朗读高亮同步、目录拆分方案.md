## T1 听书页麦克风：平时是"灭"的，只有按住时才亮

**用户原话**：听书页左下的麦克风，正常情况下应该是紧闭的，长按才可以说话；现在图标一直是亮着的。要做成灯效：只有按着的时候才闪烁/亮起来，不按的时候灭掉，看起来像一个"关了之后会灭掉的麦克风"。

**现状**：`ListenScreen.js` 约 2389–2430 行，`micHoldGesture`（长按手势）+ `micBtnEl` / `micBtnElOn` 样式；`isRecording` 为真时才有 `micBtnElOn` 背景，但图标颜色/圆环底色在静止状态仍偏亮（`EMBER.paperDim`）。

**要求**：
- **静止（未按）**：熄灭态——图标用低对比的暗灰（比背景略亮即可辨认），无光晕、无描边发亮、无呼吸动画；整体像一个"关着的灯"。
- **按住（录音中）**：点亮——图标变琥珀高亮色，外圈光晕**随收音音量呼吸/闪烁**（`metering` 已有，约 1970 行）；按下到亮起 ≤100ms，视觉上"啪"地亮。
- **松手**：淡出熄灭（约 150–250ms），回到静止态。
- 不能影响原有长按录音、语音识别、发送流程（`micGestureHandlersRef` 那套）。
- 动画尽量用 `Animated`（RN 自带，`useNativeDriver`）或已在用的 reanimated；**不要新增依赖**。

**验收**：安卓模拟器录屏/截图对比"静止 vs 按住 vs 松手"三个状态；长按录音流程回归通过；iOS 逻辑对照（注明未实机验证）。

## T2 听书朗读高亮要和声音同步

**用户原话**：听书里的高亮动效有延迟。现在的逻辑是：一段一段高亮，只高亮"前半句/前一句"，等到高亮的那一段念完，它自己又跳到下一段的前面变成高亮——并不是跟声音同步转化的，高亮效果不好。

**现状（代码已读过）**：`ListenScreen.js` 约 815–910 行。朗读按**段落**合成 TTS（`getTtsPlayUrl(paragraph, voice, rate)`），字幕高亮靠 `onCharOffset(charOffset)` 回调按"播放位置/总时长"**线性估算**当前字符偏移，再用 `sentenceIndexAtOffset` 换算成第几句。线性估算的问题：句间停顿、标点停顿、语速变化都不是线性的，所以高亮会"提前/滞后"，并且只有句级粒度。

**建议方案（先出方案给产品负责人过目，再实现）**：
- **A. 用 TTS 引擎自带的边界时间戳（推荐）**：后端用的是 Microsoft Edge TTS，`edge-tts` 库可以在合成时返回 `WordBoundary`/`SentenceBoundary` 事件（每个词/句的起始时间与文本偏移）。后端**新增**一个接口（例如 `/app/tts_with_timing`，只加不改，不动扩展在用的旧接口），返回音频 + 边界列表；前端按 `positionMillis` 二分查找当前词/句，高亮随声音走。中文的 `WordBoundary` 粒度可能是"词"或"句"，要实测。
- **B. 前端分句合成 + 分句计时**：把段落按句拆开逐句合成，用每句音频的真实时长做时间轴（请求数增加、首句延迟变化，需评估预取）。
- **C. 只优化估算**：按标点权重（句号/逗号停顿）分配时间，不改后端。成本最低但仍是估算。
- 高亮粒度目标：至少"句级实时跟随"，最好"词/短语级"渐进；被读到的部分与声音误差 ≤ 200ms。

**验收**：模拟器上播放一章，录屏逐句对照声音（可用音频波形/日志时间戳）；打断/恢复/换语速/换声音后高亮仍正确（现有的 `paragraphProgressRef`、段内恢复逻辑不能坏）。

## T3 导入书目录拆分方案（只做调研，出方案，暂不改代码）

**用户原话**：以《富爸爸》这本书为例，现在阅读目录的章节拆分方式和旧版"原版阅读"的拆分方式不一样，里面出现了非常多次"第1章""第2章"，可能是这本书的结构比较特殊；目录拆分怎么做才能更好、更适配？先探讨方案，有必要再改。

**已核实的事实（1号做过初步分析）**：
- 这本是**套装 5 册合集**：《富爸爸商学院 + 致富需要做的6件事 + 富爸爸穷爸爸 + 提高你的财商 + 财务自由之路》。EPUB 的 spine 有 **90 个文档**，`book.toc` 有 **85 个条目、最深 3 层**（册 > 部 > 章，例如"第一部分 课程"下面才是"第1章 富爸爸，穷爸爸 / 第2章 第一课…"）。
- 有 **16 个 spine 文档没有 h1–h3 标题**，**17 个文档不足 200 字**（封面、分隔页、"第一部分"这种 7 个字的页、纯图片页、版权页、目录页）。
- 现在服务端 `api/main.py` 的 `_build_standard_reading_chapters`：**只按 spine 文档一文件一章**，标题取文档里第一个 h1/h2/h3，没有标题就回退成 `第{序号}章`（代码注释里明说"TOC labels are not positional chapter content"，即**完全忽略了 EPUB 自带的目录**）。
- 后果（手机上目录可见）：开头出现两个空标题的"第1章""第2章"（封面/版权页）；每一册各自从"第1章"开始导致重复；结尾又有"第15章""第16章""第17章"这种没标题的；"第一部分 课程"这类只有一个标题的分隔页成了独立空章。
- 旧版"原版 EPUB 模式"用 epub.js 直接读 EPUB 的目录，所以看起来正常。
- 服务端另有一条更完整的路径 `_epub_book_to_chapters_via_toc`（按 `book.toc` 树分组、把"节"收进"章"），用于 PDF/EPUB 重建，**标准阅读这条没用上它**。

**待评估的方案（请逐个评估利弊，并用这本书和《原则》《未来简史》三本样书实测）**：
1. **A. 标准章节改按 `book.toc` 切分**（复用 `_epub_book_to_chapters_via_toc`）：标题、层级都准；没有 toc 的书回退旧逻辑。
2. **B. 保留 spine 切分但清洗**：把不足 N 字且无标题的文档（封面/分隔/版权/纯图片）合并进下一章或丢弃；仍无标题的用"上一章标题 + （续）"；正文里没有意义的 `第N章` 不再生成。
3. **C. 两级目录**：把 toc 的"册/部"当分组标题，手机目录做成可折叠的两级（册 > 章），同名"第1章"不再混在一起。前端目录列表在 `ReaderScreen.js`（归 1 号，动前先沟通）。
4. **D. 标题去重**：同名章节自动加册名前缀（例如"《富爸爸穷爸爸》第1章"）。
5. **E. 让用户选**："按书的目录 / 按文件"切换（工作量大，先不推荐）。
- 还要考虑：**已导入的书要不要重新拆分**（`standard_chapters` 表里已存了旧结果，`_ensure_standard_reading_chapters` 只在没有时才生成）；阅读进度用的是章节 id + 页序号（`STANDARD_PROGRESS_PREFIX:chapterId:pageIndex`），**重拆会让旧进度失效**，要给迁移办法；`highlights`/问答如果按章节 id 存，同样受影响。

**交付物**：`docs/学习笔记/` 下一份方案文档（含三本样书的实测对比：章节数、空章数、重复标题数），推荐方案 + 迁移办法 + 工作量估计。**不要改代码**，等产品负责人选定后另派。

## T4（1号已完成，供参考）阅读器上下留白

**用户原话**：阅读器上下空间用得不充分，下面总留一个拇指宽度的空，安卓和苹果都要改。
**原因**：分页是"估每页能放多少字 + 一大块保险余量（额外预留 40dp）+ 剩余不足 16% 就直接翻页"，每页文字平均只占页面高度的七八成。**做法**：改成按真实行数排版（每行字数、行高、段距全部对应页面 CSS），并用阅读容器的**实测尺寸**（`onLayout`）而不是"窗口尺寸减估计值"，安全余量降到约半行；图片页必须真放得下（旧规则允许超出 5%，实测会裁掉图片页底部）。安卓模拟器逐页实测（三种字号各 30~45 页）**0 页被裁**；iOS 用更保守的余量，**未实机验证**。详见进度记录。
